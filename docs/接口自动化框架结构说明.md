# 接口自动化框架结构说明

> 适用工程：`D:\parabank\autotest`
> 被测系统：ParaBank（本地演示网银，`http://localhost:8080/parabank/services/bank`）
> 技术栈：Python 3.13 + pytest 9.2.0 + requests 2.34.2
> 本文所有数字、耗时、输出均为本机实测，非推算。

---

## 0. 一句话概括

这套框架只做一件事：**把「怎么发请求」和「请求结果算不算对」彻底分开。**

分不开的后果很具体——44 条用例里每一处 `f"/accounts/{id}/transactions"` 都是一次手工拼 URL 的机会，每一处 `resp.json()` 都是一次因为返回 HTML 而崩溃的机会。分开之后，URL 只写一遍，崩溃只防一遍，用例里只剩下断言。

---

## 1. 全景：四层结构

```
┌──────────────────────────────────────────────────────────────┐
│  tests/                                     用例层            │
│  test_bill_pay.py (31)  test_transactions.py (44)             │
│  只写：取什么值、断言什么                                      │
└───────────────────────────┬──────────────────────────────────┘
                            │  通过夹具注入（conftest.py）
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  api/                                       接口层            │
│  bill_pay_api.py   account_api.py   transaction_api.py        │
│  只写：路径怎么拼、参数怎么编码、结果怎么取                     │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  api/http_client.py                         协议层            │
│  Resp 包装 + Session 复用 + 超时统一 + 异常归一                │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
                  requests.Session → HTTP → ParaBank :8080
```

三条硬约束：

1. **用例层不出现 URL 字符串**，只调 `tx.xxx()` / `bill_pay.xxx()`。
2. **接口层不出现断言**，只返回 `Resp`。
3. **协议层不知道任何业务接口名**，只认 path 字符串。

判断一个文件该放在哪一层，用一句话检验：**改动它会波及几处？** 波及 1 处 → 最上层；波及全部 → 最下层。

### 2.2 `http_client.py` —— 协议层

**唯一的存在理由：`resp.json()` 会抛异常，而抛异常会把「断言失败」变成「脚本崩溃」。**

具体场景：`type=CREDIT` 返回 500 + Tomcat 的 HTML 错误页（实测 4264 字节）。如果用例直接写：

```python
data = resp.json()          # ← JSONDecodeError 在这里抛出
assert data == []
```

pytest 报的是 `JSONDecodeError`，堆栈指向框架内部。CI 上看到的是「测试代码有 bug」，而不是「接口返回了 500」。**这两种失败的处理路径完全不同**（一个改测试代码，一个找开发），混在一起就失去了自动化的意义。

`Resp` 的解法：

```python
@property
def json(self):
    try:
        return self.raw.json()
    except (json.JSONDecodeError, ValueError):
        return None          # 解析失败是事实，不是异常
```

返回 `None` 的含义是：**「这份响应不是 JSON」本身也是被测行为**，应该由用例去断言，而不是由框架去崩溃。于是用例可以写成：

```python
assert resp.json is None
assert resp.is_html
assert resp.status_code == 500
```

#### `Resp` 成员表

| 成员 | 类型 | 用途 | 为什么需要 |
|---|---|---|---|
| `raw` | `requests.Response` | 逃生口 | 极少数场景要拿原始对象 |
| `status_code` | `int` | 第一判据 | — |
| `text` | `str` | 错误片段、长度 | 500 的 body 只能靠文本判断 |
| `content_type` | `str` | 区分业务拒绝/容器拒绝 | **只取 `;` 前面**，否则 `application/json;charset=UTF-8` 判等会失败 |
| `headers` | `CaseInsensitiveDict` | 少数场景 | — |
| `.json` | `Any \| None` | 正常响应 | 失败返回 `None`，不抛 |
| `is_json` / `is_html` | `bool` | 快速分类 | 500 一定是 HTML，4xx 可能是纯文本 |
| `brief(limit=200)` | `str` | 断言消息 | 500 的 HTML 有 4KB，直接塞进 `assert` 会淹没终端 |

#### `HttpClient` 的三个决策

| 决策 | 代码 | 不做会怎样 |
|---|---|---|
| 用 `Session` 而非 `requests.get` | `self.session = requests.Session()` | 每请求重新 TCP 握手，连接无法复用 |
| `Accept: application/json` 设在 Session 上 | `session.headers.update(...)` | 每个接口方法都要传一遍 header |
| 超时统一 30s | `kwargs.setdefault("timeout", self.timeout)` | 某条用例忘写 timeout，网络抖动会挂满整个 CI |

注意 `setdefault` 而不是直接赋值：**允许单条请求覆盖默认超时**，比如测超时行为时传 `timeout=1`。

### 2.3 接口层：一个业务域一个文件

三个文件不是按「接口数量」拆的，是按**业务域**拆的：

| 文件 | 暴露的方法 | 说明 |
|---|---|---|
| `bill_pay_api.py` | `pay()` / `pay_raw()` | 两个方法对应「正常调用」和「异常入参」两种形态 |
| `account_api.py` | `get()` / `balance()` / `transactions()` / `snapshot()` | **主要给断言用**——billpay 只返回一句话，对错必须回查 |
| `transaction_api.py` | 6 个查询方法 + `ids()` / `rows()` | 流水 6 个接口 |

#### 为什么 `bill_pay` 需要两个方法

```python
def pay(self, account_id, amount, payee) -> Resp:
    """正常调用：参数进 query，payee 走 JSON body。"""

def pay_raw(self, query="", body=None, content_type="application/json", send_body=True) -> Resp:
    """异常入参专用：允许自定义 query、body 原文、Content-Type。"""
```

`TestPayeeBody` 那 8 条用例要测「缺 body」「错 Content-Type」「非法 JSON」——这些用 `pay()` 表达不了，因为 `pay()` 一定会带上合法的 body 和 `application/json`。`pay_raw()` 就是为「把请求构造得不对」而存在的。

这是接口层设计的一个通用经验：**每个接口通常需要两个入口——一个「正确地调」，一个「随意地调」。** 只有前者，异常场景就只能绕到最底层去拼 requests 参数。

#### 为什么 `account_api` 的返回值不是 `Resp`

```python
def balance(self, account_id) -> Optional[Decimal]:
    resp = self.get(account_id)
    if resp.status_code != 200 or not resp.is_json:
        return None
    return Decimal(str(resp.json["balance"]))
```

它把「取余额」这个动作封装成**可直接参与运算的值**。用 `Decimal` 而不是 `float`，是因为 `0.1 + 0.2 != 0.3`——对账用例里浮点误差会直接造成假缺陷。

`snapshot()` 返回 `(余额, 流水条数)` 元组，专门服务于「付款前后各取一次，比较增量」这个模式：

```python
before = accounts.snapshot(ACCOUNT_CHECKING)
bill_pay.pay(...)
after = accounts.snapshot(ACCOUNT_CHECKING)
assert before[0] - after[0] == Decimal("0.01")
assert after[1] == before[1] + 1
```

#### 三个坑：不封装会怎样

**坑 1：URL 编码。**

```python
def _q(value) -> str:
    return quote(str(value), safe="")
```

`safe=""` 是关键，不是随手写的。它保证**空值仍然产生 `//`**：

| 写法 | 空值时的 URL | 能否复现「双斜杠 → 404」 |
|---|---|---|
| `f"/accounts/{v}/transactions"` | `/accounts//transactions` | 能，但中文/引号行为不确定 |
| `quote(v)` （默认 `safe="/"`） | 斜杠被保留，行为随请求内容变化 | 不稳定 |
| `quote(str(v), safe="")` | `/accounts//transactions` | 能，且中文/引号/空格全部确定 |

`month` 是中文（`11月`）、日期是 `MM-dd-yyyy`、注入载荷是 `0' OR '1'='1`——三种都必须在 URL 里出现且编码结果确定。这一层不统一，44 条用例里每条都要重新想一遍编码。

**坑 2：路径变更要改 44 处。** 你现在已经踩过——`/accounts/{id}/transactions` 和 `/transactions/{id}` 是两套完全不同的路径，靠封装才能保证不会在 44 个地方各写一遍。

**坑 3：防御代码重复。**

```python
@staticmethod
def ids(resp: Resp) -> set:
    """结果集 ID。响应不是数组（400/404/500）时返回空集，避免用例里到处判类型。"""
    data = resp.json
    return {t["id"] for t in data} if isinstance(data, list) else set()
```

没有它，凡是比集合的用例都得先写 `if isinstance(data, list)`。**同一种防御代码抄 30 遍**，改一处就要改 30 处。

### 2.4 核心原则：接口层不许写断言

这是整个结构里最容易犯、后果最隐蔽的错误。`transaction_api.py` 第 9 行：

> **不在这里断言**。同一个接口在正常/异常场景下的期望完全不同。

具体例子——**同一个方法、同一个入参，期望相反**：

| 用例 | 调用 | 期望 | 性质 |
|---|---|---|---|
| `test_matches_previous_year_december` | `by_month_type(12345, "12月", "All")` | 返回 2 条 | 正常 |
| `test_english_month_should_not_return_all`（xfail） | `by_month_type(12345, "Dec", "All")` | **返回全量 7 条** | 缺陷固化 |
| `test_all_is_no_filter` | `by_month_type(12345, "All", "All")` | 返回全量 7 条 | 正常 |

第三条和第二条**结果完全相同，但一条是「正确」，一条是「缺陷」**——区别只在于传入的是 `All` 还是 `Dec`，也就是调用方的意图。

封装层一旦开始判断「结果对不对」，就没法表达「这里本来就该返回全量」。所以封装层只回答两个问题：**请求发出去了吗？拿回了什么？** 判断权 100% 上移到用例。

### 2.5 `__init__.py`：6 行，但不能省

```python
from .account_api import AccountApi
from .bill_pay_api import BillPayApi
from .http_client import HttpClient, Resp
from .transaction_api import TransactionApi
```

## 3. `conftest.py`：6 个夹具 + 1 个命令行参数

### 3.1 全景表

| 夹具 | scope | autouse | 职责 | 为什么是这个 scope |
|---|---|---|---|---|
| `base_url` | `session` | — | 读 `--base-url`，去尾部 `/` | 整轮不变 |
| `client` | `session` | — | 建 `HttpClient` + 环境自检 | 连接复用、自检只需一次 |
| `clean_state` | `function`（默认，未标注） | **True** | 每用例前 `POST /initializeDB` | 数据不能跨用例传染 |
| `bill_pay` | `function`（默认） | — | `BillPayApi(client)` | 为未来状态留余地 |
| `accounts` | `function`（默认） | — | `AccountApi(client)` | 同上 |
| `tx` | `function`（默认） | — | `TransactionApi(client)` | 同上 |

外加一个**不是夹具**的函数：

```python
def pytest_addoption(parser):
    parser.addoption("--base-url", action="store", default=os.environ.get("PARABANK_BASE_URL", DEFAULT_BASE_URL))
```

### 3.2 依赖链

```
clean_state ──┐
bill_pay ─────┼──> client ──> base_url ──> request.config（--base-url）
accounts ─────┤
tx ───────────┘
```

pytest 自动按这个顺序解析，不需要手动排序。用 `--setup-show` 可以直接看到：

```
SETUP    S base_url
SETUP    S client (fixtures used: base_url)
        SETUP    F clean_state (fixtures used: client)
        SETUP    F bill_pay (fixtures used: client)
        SETUP    F accounts (fixtures used: client)
        TEARDOWN F accounts
        TEARDOWN F bill_pay
        TEARDOWN F clean_state
TEARDOWN S client
TEARDOWN S base_url
```

`S` = session，`F` = function。注意 `S` 只出现一次，`F` 每条用例出现一次。

### 3.3 `base_url` + `pytest_addoption`

```python
@pytest.fixture(scope="session")
def base_url(request) -> str:
    return request.config.getoption("--base-url").rstrip("/")
```

三级优先级：**命令行 > 环境变量 > 默认值**。

```bash
python -m pytest                                                  # 用默认值
PARABANK_BASE_URL=http://ci-host:8080/... python -m pytest        # 用环境变量
python -m pytest --base-url http://ci-host:8080/...               # 显式指定
```

`rstrip("/")` 防的是「base_url 带尾斜杠 + path 带前导斜杠 → `//`」，那会变成一次真实的路由失败。

### 3.4 `client` —— 全文件最有价值的 6 行

```python
@pytest.fixture(scope="session")
def client(base_url) -> HttpClient:
    c = HttpClient(base_url)
    # 环境自检：连不上就直接失败，不要让 30 条用例各报一次连不上
    resp = c.get("/accounts/12345")
    if resp.status_code == 0 or not resp.text:
        pytest.exit(f"ParaBank 未启动或不可达: {base_url}\n请先运行 D:\\parabank\\start-parabank.bat", returncode=1)
    yield c
    c.close()
```

#### 决策一：判据是 `status_code == 0 or not resp.text`

| 判据 | 对 500 的判断 | 后果 |
|---|---|---|
| `== 200` | 判为「不可达」 | ❌ 服务正常但数据坏了时，报「ParaBank 未启动」，误导排查方向 |
| `!= 0 and resp.text` | 判为「可达」 | ✅ 只要 TCP 通了且有响应体，就认为环境可用 |

`status_code == 0` 是 `HttpClient` 里连接失败时的值（`requests` 抛 `ConnectionError`）。**500 说明服务活着**——这是环境可用性检查和业务正确性检查的分界线。

#### 决策二：用 `pytest.exit()` 而不是 `assert`

| 方式 | 表现 | 适合 |
|---|---|---|
| `assert resp.ok` | 当前 1 条红，其余 74 条继续跑，每条都报一次「连不上」 | 业务断言 |
| `pytest.exit(msg, returncode=1)` | 整轮立即中止，输出一句带解决方案的话 | **环境不可用** |

环境不可用是**阻塞性问题**，处理方式是找运维/启动服务；用例失败是**被测系统问题**，处理方式是提单。混成 75 条红条，等于把「服务器没开」这个信息淹没了。

另外注意 `returncode=1`——它让 CI 能正确判定这一轮是失败而不是通过。

#### 决策三：`scope="session"`

- 环境自检只跑一次（实测 4.0 ms × 75 = 0.30 s 的差别）
- `requests.Session` 的连接池复用，避免 75 次 TCP 握手
- `HttpClient` 无状态（只有 `base_url` / `timeout` / `session`），session 级不会污染用例

#### `yield` 与 teardown 时机（重要）

`yield` 后面是销毁阶段。scope 决定这个阶段隔多久来一次：

| scope | `c.close()` 执行次数 | 时机 |
|---|---|---|
| `session`（当前） | **1 次** | 最后一个用到它的用例收尾之后 |
| `module` | 每个文件 1 次 | 该文件最后一条用例之后 |
| `function` | 75 次 | 每条用例之后 |

实测（`--setup-show`）确认：**中间有用例失败，不会触发 session 级 teardown**。

```
[setup] 建立资源
        test_a   → passed
        test_b   → failed        ← 这里没有 teardown
        test_c   → passed
[teardown] 释放资源              ← 直到这里才执行
```

**例外：`yield` 之前抛异常，`yield` 之后的代码不执行。**

实测发现一个容易误解的细节——`pytest.exit()` 中断时，pytest 仍然会打印 `TEARDOWN S client`，但**这不是 `close()` 执行了**：

```python
# 在 yield 之前 pytest.exit()
SETUP    S broken_check
TEARDOWN S broken_check      ← pytest 打印了，但 yield 后面的 print 没有输出
```

原因在生成器语义：`Exit` 异常在 `next(gen)` 阶段抛出，生成器**从未走到 `yield` 那一行**，对一个未启动的生成器做收尾，函数体不会执行。

在 ParaBank 这个场景下不影响正确性（进程即将退出，socket 由 OS 回收），但要清楚：**不是清理逻辑兜住了，是进程死了。**

#### 已知风险：服务中途重启

`client` 是 session 级 → 75 条用例共享同一批 keep-alive 连接。如果测试跑到一半 ParaBank 被重启（比如手动执行了 `stop-parabank.bat`），连接池里缓存的是已失效连接，后续请求会抛 `ConnectionError`；而夹具的 setup 只在整轮开始时跑过一次，**没有机会重新自检和重建**。

三种处理，按代价排序：

| 方案 | 做法 | 适用 |
|---|---|---|
| 什么都不做 | — | 当前规模（整轮 5.7 秒）够用 |
| 加重试 | `HTTPAdapter(max_retries=Retry(...))` | 远程/不稳定环境 |
| 降为 function scope | 每条用例重建 client | 有登录态、会掉线的系统 |

**第三种在 ParaBank 上不该选**：75 次建连 + 75 次 `close()`，换不来任何收益——ParaBank 无登录态，不需要按用例重置会话。

### 3.5 `clean_state` —— 唯一使用 `autouse=True` 的夹具

```python
@pytest.fixture(autouse=True)
def clean_state(client):
    """每个用例前把库恢复干净基线，保证用例可独立重复执行。"""
    resp = client.post("/initializeDB")
    assert resp.status_code == 204, f"数据重置失败: {resp.brief()}"
    yield
```

#### 为什么必须 autouse

如果它不是 autouse，75 条用例的签名里都得写 `clean_state`。只要有 3 条漏了，这 3 条就会读到上一条留下的脏数据——**而且它们大概率仍然是绿的**（因为恰好没断言到受影响的字段），直到某天数据分布变化才突然变红。

autouse 保证的是「没有后门」。

#### 为什么断言放在 `yield` 之前

重置失败时立刻停在 setup 阶段，用例根本不会开始执行。否则你会看到「断言余额不对」，然后花半天查业务逻辑，实际是库没重置成功——**报错位置与真实原因分离，是最浪费时间的一类问题**。

#### 代价（必须知道的三条）

| 代价 | 量化 / 表现 |
|---|---|
| 每条用例 +72.5 ms | 75 条 × 72.5 ms ≈ **5.44 s**，占整轮 5.74 s 的 **95%** |
| 用例之间隐性顺序耦合 | 它假设「每条用例开始时必须有干净库」，所以**不能 `pytest-xdist -n 4` 并行**——4 个进程同时 `initializeDB` 会互踩 |
| 报错不指向它 | 数据没重置成功时，报的是业务断言红，不是夹具红 |

第二条是结构性限制，不是「优化一下」能解决的。想并行必须改模型：**从「每条用例重置全库」改为「每条用例独占账户」**。

#### `autouse` 的作用范围

取决于 `conftest.py` 放在哪：

| 文件位置 | 作用范围 |
|---|---|
| `autotest/conftest.py`（当前） | `tests/` 下全部用例 |
| `autotest/tests/conftest.py` | 仅 `tests/` 目录 |
| `autotest/tests/smoke/conftest.py` | 仅该子目录 |

**这不是全局注入。** 所以如果以后在 `tests/e2e/` 下要写「连续付款 3 次累积」的场景，可以在该子目录放一个不同的 conftest 覆盖掉 `clean_state`——这是 autouse 唯一体面的退出方式。

---

### 3.6 三个 API 包装器夹具

```python
@pytest.fixture
def tx(client) -> TransactionApi:
    return TransactionApi(client)
```

看起来是多余的一行，换来两个东西：

**① 用例签名自解释。**

```python
def test_pay_deducts_balance_exactly(self, bill_pay, accounts):
def test_list_sorted_by_date_then_id(self, all_txs):
```

一眼能看出第一条在「调用付款接口，再回查账户余额对账」。如果全写 `client`，就看不出被测对象是谁。

**② 换实现时不动用例。** 哪天 `TransactionApi` 需要注入 token 或重试策略，改这一行就够。

**为什么 scope 是 function（默认）：** 现在它只存一个 `client` 引用，创建成本近似 0。选 function 是**为未来留余地**——如果哪天它需要保存「本次请求的上下文」，function 级才不会串到下一条用例。标成 session 会埋隐患：某条用例改了实例属性，下一条读到脏值，而且**用例签名上看不出来**。

### 3.7 用例文件内的局部夹具

`tests/test_transactions.py` 里还有一个**不属于 conftest** 的夹具：

```python
@pytest.fixture
def all_txs(tx):
    """当前快照下的全量流水，已按 (date, id) 升序。"""
    resp = tx.list_by_account(ACCOUNT)
    assert resp.status_code == 200, resp.brief()
    return tx.rows(resp)
```

放在用例文件里而不是 conftest，因为**只有这个文件的用例需要它**。判定标准：

| 夹具放哪 | 判断依据 |
|---|---|
| `conftest.py` | 跨文件复用（`client` / `clean_state` / `tx`） |
| 用例文件 | 单个文件内复用（`all_txs`） |

注意它内部的 `assert`——这是夹具里唯一允许的断言类型：**断言前提成立**（「能拿到全量流水」），不是断言业务正确。

## 4. `@pytest.fixture` 参数详解

### 4.1 `scope`：建几次

默认值 `"function"`。**不写就等于 `scope="function"`**：

```python
@pytest.fixture(autouse=True)
def clean_state(client): ...        # 等价于 scope="function", autouse=True
```

| scope | 创建时机 | 本项目 75 条用例会建几次 |
|---|---|---|
| `function`（默认） | 每条用例一次 | 75 |
| `class` | 每个测试类一次 | 15 个类 |
| `module` | 每个 `.py` 文件一次 | 2 |
| `package` | 每个包一次 | 1 |
| `session` | 整轮一次 | 1 |

**「创建一次」的准确含义是「第一次有人需要时才创建」**，不是「启动时创建」。只运行 `test_transactions.py` 时，`bill_pay` 夹具根本不会被创建。

**销毁顺序：宽 scope 后创建、先销毁。** 因为宽 scope 必须活到最后。

---

### 4.2 `scope` 不写会怎样：逐夹具推演

#### `client` 改成 function 级

| 变化 | 实测代价 |
|---|---|
| 环境自检从 1 次 → 75 次 | 4.0 ms × 75 = **0.30 s** |
| `Session` 建 75 次、`close()` 75 次 | 连接池失效，每请求重新 TCP 握手 |
| 服务挂掉时 | 仍只报一次（`pytest.exit` 立即中止），**这点不受影响** |

0.3 秒在本地不算多，但换远程环境后，连接复用与否的差距是秒级。**session 级夹具的核心价值是「连接复用」，不是「省几次请求」。**

#### `clean_state` 改成 session 级（最危险的改法）

```python
@pytest.fixture(scope="session", autouse=True)   # ← 不要这么做
def clean_state(client): ...
```

它会在整轮开始前重置一次，然后 75 条用例共享同一份被不断写脏的数据。表现是：**单跑一条绿，跑全量红，而且红的顺序不固定**（`-k` 筛选、随机顺序插件都会改变执行顺序）。

这类失败最难查——它看起来像业务 bug，实际是夹具问题。

#### `tx` / `accounts` / `bill_pay` 保持默认

创建成本接近 0，function 级没有额外开销，而且能隔离未来可能出现的实例状态。

---

### 4.3 `autouse`：要不要主动申请

默认 `False`。`autouse=True` 的含义：**作用范围内的每条用例都自动使用它，不需要在函数签名里写参数名。**

```python
# 有 autouse
def test_xxx(self, tx):              # clean_state 自动执行

# 没有 autouse 且无人引用
@pytest.fixture
def some_fixture(): ...
# → 定义了但永远不会执行，也不会有任何提示
```

这是最容易静默出错的地方：**写了夹具、没人引用、然后以为它生效了。**

不用的三个代价：

| 代价 | 表现 |
|---|---|
| 读用例看不出它存在 | 只看 `def test_xxx(self, tx)` 完全不知道背后有 `initializeDB` |
| 报错不指向它 | 数据没重置成功时，报的是业务断言红 |
| 阻碍并行 | `pytest-xdist -n 4` 时多进程同时重置会互踩 |

---

### 4.4 其他参数

| 参数 | 作用 | 例子 |
|---|---|---|
| `params=[...]` | 一个夹具生成多条用例 | `@pytest.fixture(params=["json", "xml"])` → 用到它的每条用例跑 2 遍 |
| `ids=[...]` | 给 `params` 起可读名字 | `ids=["json格式", "xml格式"]` |
| `name="..."` | 换夹具名 | `@pytest.fixture(name="tx")` |

`params` 是这三个里最有用的，但**本项目不该用**——`@pytest.mark.parametrize` 更直接，且能同时参数化多个维度。`params` 只适合「一个环境维度影响所有用例」的场景，比如 `base_url` 换成 `["dev", "staging"]` 做环境矩阵。

---

### 4.5 `scope` 的四条硬规则

**① 宽 scope 不能依赖窄 scope。**

```python
@pytest.fixture(scope="session")
def client(base_url, clean_state):   # ← 报错
```

```
ScopeMismatch: You tried to access the function scoped fixture clean_state
with a session scoped request object
```

原因很直接：`client` 只建一次，`clean_state` 要建 75 次——**没法在「只建一次」的时候调用「要建 75 次」的东西**。这也是 `client` 里只能做一次环境自检、不能做数据重置的根本原因。

**② 只有 `yield` 之前的代码在创建时跑，`yield` 之后的在销毁时跑。**

```python
def client(base_url):
    c = HttpClient(base_url)     # 创建时
    yield c
    c.close()                    # 销毁时（session 末尾）
```

写成 `return c` 的话，`c.close()` 永远不会执行，连接泄漏。

**③ 夹具名就是用例的形参名，拼错报 `fixture 'xx' not found`。**

这个错误和 `NameError` 很像，新人常浪费时间去查拼写之外的原因。

**④ `scope` 影响「实例」，不影响「副作用」。**

`client` 是 session 级，但**每次 `client.get()` 都是一个真实 HTTP 请求**。scope 只决定 `HttpClient` 这个 Python 对象建几次，不决定请求发几次。这是两个独立维度。

---

### 4.6 判断 scope 的一句话标准

> **「这个东西坏了、脏了、或者很贵，会不会跨用例传染？」**

| 情况 | 选择 | 本项目对应 |
|---|---|---|
| 会传染，且创建便宜 | `function` + `autouse=True` | `clean_state` |
| 不传染，但创建贵 | `session` | `client`、`base_url` |
| 都不占 | 默认 `function` 即可 | `tx`、`accounts`、`bill_pay` |
| 只在单文件复用 | 写在该用例文件里 | `all_txs` |

## 5. `data/` —— 数据层

```
data/
└── payee_data.py     Payee 工厂 + 基线账户常量
```

```python
ACCOUNT_CHECKING = 12456   # 余额 10.45，做小额支付刚好
ACCOUNT_ZERO = 12900       # 余额 0，测零余额
ACCOUNT_NEGATIVE = 12345   # 余额 -2300，测负余额
ACCOUNT_RICH = 54321       # 余额 1351.12

def payee(name="Test Payee", ...) -> dict:
    return {"name": name, "address": {...}, ...}
```

**为什么用工厂函数而不是常量 dict：**

```python
PAYEE = {"name": "Test Payee", ...}          # ❌ 所有用例共享同一个可变对象

def payee(**kwargs) -> dict:                 # ✅ 每次返回新 dict
    return {...}
```

某个用例写了 `p["name"] = "改名"`，后面所有用例都会受影响——**可变对象串用例是接口自动化里最常见的事故**。而且工厂函数天然支持「只改一个字段」：

```python
payee(name="张三")                            # 其余字段用默认
payee(address={"street": "1 A St", ...})      # 只改地址
```

**注意**：账户常量和流水常量（`ACCOUNT = 12345` / `ALL_IDS` / `CREDIT_ID = 12145`）放在各自的用例文件顶部，因为它们只被单个文件使用。这是「作用域最小化」的同一个原则。

## 6. 用例层的组织方式

### 6.1 按测试目的分组，不按接口堆

内部分组（类名即测试目的）：

| `test_bill_pay.py` | 条数 | | `test_transactions.py` | 条数 |
|---|---|---|---|---|

| `TestContract` | 2 | | `TestTypeParameter` | 5 |
| | | | `TestDateParameters` | 6 |
| | | | `TestCrossEndpointConsistency` | 4 |
| | | | `TestErrorContract` | 3 |

数量差异说明：静态 `def test_` 只有 39 / 29 个，`parametrize` 把它们展开成 44 / 31。

### 6.2 marker 体系

`pytest.ini`：

```ini
markers =
    billpay: /billpay 接口用例
    transactions: 流水查询接口用例
    happy: 正常业务路径
    boundary: 金额与数值边界
    validation: 必填参数与请求体校验
    consistency: 幂等与数据一致性
    contract: 契约与错误响应格式
```

两层标记：

| 层级 | marker | 用途 |
|---|---|---|
| 模块级 | `pytestmark = pytest.mark.transactions` | 按接口筛选：`-m transactions` |
| 类级 | `@pytest.mark.boundary` | 按测试目的筛选：`-m boundary` |

`--strict-markers` 保证写错的 marker 直接报错，而不是静默失效。

### 6.3 xfail 的写法

27 条 xfail 严格对应契约表里的缺陷，且**都用 `strict=True`**：

```python
@pytest.mark.xfail(
    strict=True,
    reason="契约缺口 6.3：month 无法识别时静默返回全量，调用方无法察觉过滤失效",
)
def test_english_month_should_not_return_all(self, tx):
    ...
```

`strict=True` 的作用：**开发修好后，它会变成 XPASS，也就是「失败」**。这样你会被强制提醒去摘标记——而不是让一条永远 xfail 的用例在仓库里躺着，谁也不知道它已经失效。

这就是「用测试固化缺陷」的价值：**缺陷单会自己告诉你它被修了。**

## 7. 一次请求的完整调用链

以 `test_list_returns_all_seven(tx)` 为例：

```
① pytest 收集到 test_list_returns_all_seven
② 解析夹具：tx → client → base_url
     client 是 session 级 → 首次创建，执行环境自检（GET /accounts/12345）
     tx 是 function 级 → TransactionApi(client)
     clean_state 是 autouse → POST /initializeDB（72.5 ms，断言 204）
③ 进入用例体：tx.list_by_account(12345)
④ TransactionApi.list_by_account
     _q(12345) → "12345"
     拼 path：/accounts/12345/transactions
⑤ HttpClient.get
     url = base_url + path
     kwargs.setdefault("timeout", 30)
     session.request("GET", url)          ← 真正的网络调用
⑥ Resp(raw) 包装：status_code / text / content_type
⑦ 回到用例：resp.status_code == 200，tx.rows(resp) → list
⑧ 断言 len(rows) == 7，ids == ALL_IDS
⑨ teardown：clean_state → tx → client（session 末尾才执行 close）
```

关键点：**第 ③ 步之后，用例再也不会碰到 URL 字符串、`requests`、`resp.json()` 的异常处理。** 这就是分层的实际收益。

## 8. 已知短板与改法

| 问题 | 表现 | 改法 | 优先级 |
|---|---|---|---|
| `account_api.transactions()` 与 `transaction_api.list_by_account()` 重复 | 两个方法打同一接口 | 二选一，`account_api` 只保留 `balance` / `snapshot` | 低 |
| 断言辅助散落各处 | `TransactionApi.ids()` / `AccountApi.balance()` 风格不一 | 抽 `assertions.py`：`ids_of` / `is_error` / `same_set` | 中 |
| `clean_state` 与 session 级 `client` 冲突 | 无法 `pytest-xdist -n 4` | 改为「每条用例独占账户」而非「重置全库」 | 低（规模未到） |
| 无重试机制 | 服务中途重启导致后续全红 | `HTTPAdapter(max_retries=Retry(...))` | 中 |
| `client` 不支持认证态 | 换成要登录的系统时无处放 token | 加 `login()` 方法 + session 级 fixture | 按需 |

前三条不影响正确性，只影响可维护性。**第四条是唯一会在实际使用中咬人的**——ParaBank 重启很频繁。

## 9. 新增一个接口域的步骤清单

假设要加 `/customers/{id}/accounts`：

- [ ] **1. 先出契约**：用 `probe/` 那套方法探明参数格式、合法/非法值行为、状态码分层。不要照着文档写用例——这个项目的文档已经错过一次（`month` 只认中文，文档没写）
- [ ] **2. 写契约表**：`docs/xxx接口契约表.md`，把「规则」和「快照」分开记
- [ ] **3. 接口层**：`api/customer_api.py`，每个接口两个入口（正常调 / 随意调），路径参数统一 `_q()`
- [ ] **4. 出口**：`api/__init__.py` 加导出
- [ ] **5. 夹具**：`conftest.py` 加 `customers(client)`
- [ ] **6. marker**：`pytest.ini` 加 `customers: ...`
- [ ] **7. 用例**：`tests/test_customers.py`，`pytestmark = pytest.mark.customers`，按测试目的分 5–9 个类
- [ ] **8. 跑两遍**：确认可重复（同一份代码跑两次结果一致）
- [ ] **9. 跑全量**：确认没破坏已有基线（当前应为 75 条）

**验证分层是否合理的标准**：如果第 3–7 步中发现要改 `http_client.py` 以外的东西，说明分层有问题，现在改比以后改便宜。
