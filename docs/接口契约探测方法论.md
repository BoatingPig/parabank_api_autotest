# 接口契约探测方法论

> 以 ParaBank 流水查询模块（6 个接口 / 12 个参数位 / 106 条探测矩阵）为实例
> 编制日期：2026-11-21

---

## 序：这套东西在解决什么问题

写接口用例，本质是写「给定输入 X，响应**应该是** Y」。

问题在「应该」两个字：**你凭什么知道 Y 是什么？**

- 看文档？文档可能过时、可能只写了好路径。
- 凭常识？REST 惯例只能覆盖状态码，覆盖不了业务语义。
- 看代码？代码告诉你「实现是什么」，不告诉你「承诺是什么」，而且它可能是错的。
- 看数据库？数据库只知道「数据是什么」，不知道「参数该不该生效」。

**契约探测就是在写用例之前，用一批实验把「应该」变成「实测过的事实」。**

这套方法产出四样东西：

| 产物 | 回答的问题 | 形态 |
|---|---|---|
| 矩阵 `matrix.csv` | 我传了什么，系统回了什么 | 原始观测，106 行 |
| 缺陷清单 `findings.csv` | 哪里偏离了预期 | 结论，26 条 |
| 契约表 | 正常规则是什么 | 文档，6 接口 × 12 参数位 |
| 测试用例 | 怎么持续守住这些规则 | 代码，约 40 条 |

注意顺序：**矩阵在前，结论在后；事实在前，判断在后。** 这个顺序颠倒了，后面全是自说自话。

## 一、为什么写用例之前要先做契约表

### 1.1 跳过这一步的三种失败方式

**第一种：把文档当真相，写出「永远通过」的用例。**

文档写「支持按月份查询」，你就写 `month=11月 → 断言 200 + 非空`。这条用例会永远通过，因为它只验证了「接口没崩」，没验证「月份真的生效了」。

更糟的情况：`month=Nov` 返回 200 + 全量 7 条，你的断言 `status == 200 and len > 0` **照样通过**。参数完全没生效，用例却是绿的。

**第二种：把常识当真相，写出「批量误报」的用例。**

常识说「不存在的资源该返回 404」，于是你断言 `accountId=99999 → 404`。实测返回 200 + 空列表。
于是你报了一条缺陷。开发回你：「文档写的就是返回空列表，这是设计。」你的可信度就掉了一格。

**第三种：拿一条路径的结论套所有路径。**

`accountId=0` 在 `/accounts/{id}/transactions` 上返回 400，你据此认为「账户不存在一律 400」。实际另外 4 个接口返回 200 + 空。

单看每个接口都对，横着摆才矛盾——**而这种矛盾，不横向对齐是发现不了的**。

### 1.2 契约的三个来源，各有盲区

| 来源 | 能告诉你 | 盲区 |
|---|---|---|
| 接口文档 | 设计意图、字段含义 | 可能过时、可能只写正常路径、可能和实现不一致 |
| 源码 | 实现细节、边界处理 | 只反映「怎么做的」，不反映「该怎么做」；读得懂代码不等于测得出行为 |
| **实测** | 真实行为，含所有 bug | 只覆盖你想到的输入；单条实测看不出「异常」，必须横向对比 |

**结论：三者都要用，但参照系必须是实测。** 文档和源码用来「解释」实测，不用来「代替」实测。

这也是本方法的一个基本立场：**先测，再解释；不要解释了才去测。**

### 1.3 契约表和测试用例的分工

| | 契约表 | 测试用例 |
|---|---|---|
| 性质 | 知识 | 断言 |
| 变化频率 | 低（接口行为变了才改） | 中（策略调整、覆盖度调整） |
| 读者 | 人 | 机器 |
| 失效方式 | 过时（写了旧行为） | 误报（断言错）或漏报（没断言） |

契约表是「说明书」，用例是「守门员」。**先有说明书，守门员才知道该守什么。**

没有契约表直接写用例，等于让守门员自己猜球门在哪。

## 二、整体流程

```
① 定义被测面          ② 设计矩阵           ③ 执行            ④ 分析
   config.py     →     values.py +      →   runner.py    →   analyze.py
   6 接口/12 组        render.py            matrix.csv       findings.csv
                       106 条 case          106 行观测       26 条结论
                                                                  ↓
                                                          ⑤ 提炼契约表
                                                              ↓
                                                          ⑥ 编写用例
```

每一环的产物都是下一环的**唯一输入**。这个约束很重要：分析阶段不再去请求服务，只读 `matrix.csv`。这样结论可以离线复现，也能拿去和别人对账。

## 三、第一步：定义被测面

### 3.1 接口清单：不要凭印象

最初以为流水查询只有 4 个接口。实际扫 OpenAPI / 路由表，发现是 6 个——漏了 `/accounts/{id}/transactions`（全量列表）和 `/transactions/{id}`（单条）。

**教训：接口清单必须来自可枚举的来源**（OpenAPI 文档、`@Path` 注解扫描、网关路由表），不能靠「我记得有这几个」。

### 3.2 参数位是分组单位，不是接口

一个接口有 3 个参数，就要拆成 3 组。原因是**控制变量**：

测 `month` 时，`accountId` 和 `type` 必须固定住；测 `type` 时，`month` 和 `accountId` 必须固定住。如果把一个接口的参数混在一起测，返回值变化时你无法归因。

本项目 6 个接口拆出 **12 个参数位（组）**：

| 接口 | 参数位 |
|---|---|
| `tx_by_id` | transactionId |
| `tx_by_account` | accountId |
| `tx_by_account_amount` | accountId、amount |
| `tx_by_account_month_type` | accountId、month、type |
| `tx_by_account_daterange` | accountId、fromDate、toDate |
| `tx_by_account_ondate` | accountId、onDate |

### 3.3 baseline：整个方法的参照系

每个参数位有一个 baseline 值，含义是「合法、且能查出非空结果」。

它有三个作用：

1. **控制变量**：测 A 参数时，其余参数全取 baseline，保证归因唯一。
2. **正向对照**：baseline 本身作为一条 case 存在，用来证明「这个接口在当前环境下是好的」。
3. **比较基准**：所有变体的结果集都要和它比。

**baseline 必须实测确认非空。** 这条规则是踩出来的：

> 最初给 `onDate` 设的 baseline 是 `11-11-2026`，凭印象觉得「11 月中旬应该有数据」，没查。
> 实测 0 条。整组 15 条变体全部返回 200 + 0 条，**无法归因**——分不清是参数有问题，还是这天本来就没数据，整组数据作废。
> 改成 `11-09-2026`（实测 2 条）后才恢复。

为什么必须非空？因为空集做参照系，所有集合关系都会退化：

```
正常：base = {13255, 13477}        变体 = {13255}        → 真子集 → 过滤生效
基线空：base = {}                  变体 = {13255, 13477} → 超集   → 误判"方向错"
基线空：base = {}                  变体 = {}             → 全等   → 误判"没生效"
```

同一个变体，仅因为参照系从 2 条变成 0 条，结论完全反过来。

## 四、第二步：设计测试矩阵

### 4.1 为什么叫「矩阵」不叫「用例」

| | 测试用例 | 测试矩阵 |
|---|---|---|
| 前提 | 已经知道期望值 | **不预设期望值** |
| 目的 | 验证已知规则 | 发现未知规则 |
| 产物 | 通过 / 失败 | 一批观测，供横向对比 |
| 判据 | 断言 | 与基线比较 + 语义预期 |

关键差别是**不预设期望值**。

一旦给每个值预设「应该返回什么」，你就只能验证你想到的东西，想不到的一律漏掉。矩阵的做法是：先只记录「实际返回了什么」，等全部结果摆在一起，差异自己会浮出来。

`month=Nov` 就是个例子。如果你预设「Nov 应该返回 5 条」，测得 7 条，你会判它失败——但如果预设是「Nov 应该报错」呢？测得 7 条也算失败。**两种预设都指向「有问题」，但说不出是哪种问题。** 而矩阵的方式是：先记下「7 条 = 全量」，再和基线比，关系是「全等」，于是结论精确到「条件压根没加上」。

### 4.2 值库：只放变体，合法值由 baseline 提供

`values.py` 里 5 套值库，按参数类型分组：

| 值库 | 数量 | 设计思路 |
|---|---|---|
| `int` | 8 | 边界（0/负数/1）、类型错（abc/1.5）、溢出（2147483648）、空、注入 |
| `decimal` | 8 | 等值（300.00）、零值、负数、科学计数法、精度变体、非数字 |
| `enum` | 8 | 合法值、魔法值 All、大小写变体、空、注入 |
| `month` | 9 | 中文月份、数字、英文全称/缩写、ISO 格式、空、注入 |
| `date` | 7 | 合法日期、ISO 格式、非法月日、2 月 30 日、全零、空 |

**关键设计：值库里不放合法值。**

合法值由 `config.baseline` 提供，并且单独作为一条 baseline case 产出。如果值库里也放一份 `12345`，就会出现两条一模一样的 case，分组统计也会重复计数。

（这条规则是改出来的：初版值库里放了 `12145`，导致 `tx_by_id` 组出现两条相同的基线行。）

### 4.3 控制变量：一次只动一个参数

`render.py` 为每个参数位生成 case 时，做法是：

```
组 (endpoint, param) 的 case = 
    baseline 全量参数
    但把 param 替换成 values[param] 里的每一个值
```

代码上拆成 `param_cases()` 函数，用 `others` 收集「其余参数」：

```python
def param_cases(endpoint, param, value):
    others = {k: v for k, v in endpoint["baseline"].items() if k != param}
    others[param] = value
    return others
```

这样 `tx_by_account_month_type` 组的每条 case 都是：

| case | accountId | month | type | 变动的是 |
|---|---|---|---|---|
| C046 | 12345 | All | All | baseline |
| C047 | 12345 | **11月** | All | month |
| C057 | 12345 | All | **Credit** | type |

如果同时动 month 和 type，测得 0 条时无法判断是哪个参数导致的。

### 4.4 106 条是怎么算出来的

```
12 个参数位 × 每组 7~9 个变体 = 94 条变体
+ 12 条 baseline
= 106 条
```

每个参数位的变体数不完全相同（month 有 9 个，日期类有 7 个），因为值库大小是按「这个类型的错误有哪些形态」定的，不是凑整。

## 五、第三步：跑出 matrix

### 5.1 matrix 是什么

一张宽表，**一行 = 一次请求**，13 列：

| 列 | 含义 | 为什么要有 |
|---|---|---|
| `case_id` | 唯一编号 | 回指、复现、跨文件关联 |
| `endpoint` | 接口名 | 分组键之一 |
| `param` | 本组被测的参数位 | 分组键之一 |
| `value` | 本次传的值 | 结论里的「哪个值」 |
| `is_baseline` | 是否基线 | 参照系标记 |
| `url` | 完整请求 URL | 能直接粘到浏览器/Postman 复现 |
| `status` | HTTP 状态码 | 第一层判据 |
| `content_type` | 响应类型 | 区分「业务拒绝」和「容器拒绝」 |
| `result_count` | 结果条数 | 快速扫量 |
| `result_ids` | 结果 ID 列表 | **集合比较的唯一依据** |
| `body_len` | 响应字节数 | 辅助判断（空 body = 没进业务层） |
| `elapsed_ms` | 耗时毫秒 | 只作参考，本方法不对响应时间下结论 |
| `error_snippet` | 错误响应片段 | 写证据时直接引用 |

### 5.2 为什么存 `result_ids` 而不只存 `result_count`

因为**条数相同不代表结果相同**。

`amount=300` 返回 1 条（12145），`amount=0` 也返回 1 条（13699）。只比条数，两者「相同」；比集合，两者毫无关系。

更进一步：判断「参数有没有生效」必须比集合，不能比大小。

```
month=All  → 7 条 {12145,12256,12589,13255,13477,13699,14143}
month=Nov  → 7 条 {12145,12256,12589,13255,13477,13699,14143}   ← 逐条相同 = 没生效
month=11月 → 5 条 {12589,13255,13477,13699,14143}                ← 真子集 = 生效
```

三者的「条数」只分出两种（7 和 5），但「关系」分出三种（全等 / 全等 / 真子集）。前者会把 `Nov` 和 `All` 混为一谈。

### 5.3 matrix 的三个用途

1. **判定**：所有结论的唯一数据源。分析脚本只读它，不再请求服务。
2. **复现**：`url` 列可以直接粘出去，任何人能重跑出同样结果。
3. **对账**：`result_ids` 能和数据库、能和另一个接口的返回交叉验证。

### 5.4 跑之前必须 sanity check

`runner.py` 里硬编码了 3 条已知答案：

```
/transactions/12145                        → 200 / 1 条 / 首条 id=12145
/accounts/12345/transactions               → 200 / 7 条
/transactions/abc                          → 404 / 0 条
```

**这三条不过，106 条结果全部是垃圾。**

原因：如果 Tomcat 没起来，106 条全是 connection refused；如果数据库没初始化（重启后是空库），106 条全是 200 + 0 条；如果 XML 解析正则坏了，`result_ids` 全是空。这三种情况下，分析脚本会「正常」跑完，产出一份看起来合理的报告。

sanity check 同时也是 warm-up：第一次访问 ParaBank 会触发初始化，先打三条探针，把冷启动开销挡在正式测试之外。

## 六、第四步：分层过滤成 findings

这一节回答「有几层判断，为什么这么分层」。

### 6.1 六层，每层回答一个问题

| 层 | 名称 | 回答的问题 | 输入 | 输出 |
|---|---|---|---|---|
| 1 | 载入 + 派生 | 数据能参与运算吗 | CSV 字符串 | 带类型和派生字段的行 |
| 2 | 前置校验 | 数据可信吗 | 全部行 | 根因告警（0~1 条/组） |
| 3 | 集合关系 | 差异是什么形状 | 变体 + 基线 | 6 种关系之一 |
| 4 | 逐条判定 | 这个形状意味着什么 | 关系 + 语义预期 | 缺陷类型 |
| 5 | 横向检查 | 换个角度看有矛盾吗 | 跨组、跨接口 | 一致性缺陷 |
| 6 | 落盘 | 怎么让人看懂 | 全部结论 | findings.csv |

为什么不全写成一个函数？三个理由：

1. **每层的失败模式不同**。第 1 层错（类型没转），全部结论错；第 4 层错（预期写漏），只有部分结论错。合成一个函数，出了问题无法定位是哪一层。
2. **可以单独关闭**。第 5 层不需要预期，第 4 层需要。分开写，加新检查不影响老检查。
3. **对应人的思考顺序**。「数据能用吗 → 可靠吗 → 差在哪 → 是什么问题 → 还有别的角度吗 → 怎么表达」，这本来就是人排查的步骤。

### 6.2 第一层：类型与结构归一

CSV 读出来**全是字符串**。不转换会踩一个静默的坑：

```python
r["status"] != 200      # "200" != 200 → 恒为 True
```

初版就是这个错误，把 94 条变体全部判成「拒绝」。

这一层做三件事：

| 动作 | 代码 | 目的 |
|---|---|---|
| 类型转换 | `int(r["status"])` | 能比较 |
| 结构转换 | `set(result_ids.split(","))` | 能做集合运算（`<`、`>`、`&`） |
| 派生字段 | 反查 `kind`、计算 `cls` | 后续不用重复查 config，分类口径统一 |

`cls` 把状态码压成 `2xx/3xx/4xx/5xx` 四档。后面的比较全部基于档位，不基于具体码值——因为契约关心的是「这一类响应」，不是「500 还是 502」。

### 6.3 第二层：三道闸

**闸 1：baseline 合法（200 且非空）**

参照系失效时，第 3 层会产出大量假缺陷。与其让 7 条变体各报一条「超集」，不如在闸门上报 1 条「基线坏了」。

代码里有配套的短路：

```python
if rel == "nobase":
    return None    # 根因已在闸 1 报过，这里不再制造噪音
```

**一条根因一条结论，而不是一条根因 N 条症状。**

**闸 2：`result_count == len(result_ids)`**

这两个值来自**两条独立路径**：

```python
"result_count": body.count("<transaction>"),                    # 数字符串
"result_ids":   TRANSACTION_ID_RE.findall(body),                # 正则抓 <id>数字</id>
```

一条数标签，一条抓子元素，互不知情。对不上说明**自己的解析器坏了**，与服务器无关。

能挡住：某个 id 不是纯数字（`TXN12145`）、描述字段里混进未转义的 `<id>`、某条交易缺 `<id>` 子元素。
挡不住：整个响应换成 JSON（两边都变 0，「一致」通过）。

挡不住的那种情况，由闸 1 兜底——因为换格式后基线也会变空。**两道闸是互补的，不是重复的。**

**闸 3：语义预期覆盖**

`expect.py` 查不到预期时，返回 `None`，立刻变成 `NO_EXPECTATION`，并计入覆盖率统计。

为什么不能「查不到就放过」？因为那样报出的「94 条通过 90 条」是假的——真实情况可能是 60 条真通过，30 条**压根没被判过**。

**测试工具最危险的失败不是误报，而是漏判且把漏判算作通过。**

### 6.4 第三层：集合关系

把变体结果集和基线结果集比，得到 6 种关系之一：

| 关系 | 含义 | 典型根因 |
|---|---|---|
| `noop` 全等 | 逐条相同 | 条件没加进查询 |
| `subset` 真子集 | 变少且包含 | 过滤生效 |
| `superset` 超集 | 变多且包含 | 条件方向错了 |
| `cross` 交叉 | 有重叠不互含 | 条件串错了字段 |
| `disjoint` 无关 | 零交集 | 用了完全不同的字段 |
| `empty` 空 | 变体为空 | 过滤掉全部，或参数被误解析 |

**判断顺序有讲究：先判空、再判全等、最后判包含关系。**

```python
if not base: return "nobase"      # 1. 参照系无效
if not ids:  return "empty"       # 2. 空集优先
if ids == base: return "noop"     # 3. 全等
if ids < base:  return "subset"   # 4. 真子集
if ids > base:  return "superset" # 5. 超集
if ids & base:  return "cross"    # 6. 交叉
return "disjoint"                 # 7. 无关
```

如果先判包含关系，空集是**任何集合的子集**，`ids < base` 会成立，`empty` 就被吞成 `subset`——「过滤掉全部」和「过滤掉一部分」混为一谈，而这两者的缺陷性质完全不同。

**这一层只产出形状，不下结论。** 同一个「全等」，在 `month` 上是「参数没生效」（缺陷），在 `fromDate=01-01-2026` 上是「下界拉到年初，本来就该全含」（正确）。判对判错留给下一层。

### 6.5 第四层：语义判定

需要两个输入：形状（第 3 层）+ 语义预期（`expect.py`）。

`expect.py` 用三级查找决定「这个值应该怎样」：

```python
(param, value)  →  (kind, value)  →  (kind, "*")
```

- 第一级只放「换个参数位语义就变」的值。目前只有日期：`11-11-2026` 在 `onDate` 上应得 0 条，在 `fromDate` 上应得 1 条，在 `toDate` 上应得 4 条。**同一个值，三个正确结果。**
- 第二级按类型匹配具体值。
- 第三级通配，一条 `("int", "*") → ("reject", "empty")` 覆盖 48 条变体。

预期有五种语义：

| 语义 | 含义 | 可接受的关系 |
|---|---|---|
| `noop` | 魔法值（`All`），语义是「不过滤」 | 必须全等 |
| `filter` | 生效并收窄 | 必须是真子集 |
| `key` | 键值匹配（`amount`） | 与基线无关，但每条必须命中该值 |
| `empty` | 合法值，库里确实没有 | 必须是空 |
| `reject` | 非法输入 | 必须 4xx |

**一个值可以写多个语义。** `month="Nov"` 写成 `("filter", "reject")`：认了就过滤，不认就报错，两种都放行——唯一不能接受的是「静默返回全量」。

为什么允许两种？因为文档没说 `Nov` 算什么。与其猜一个「正确答案」然后误报一堆，不如把「不确定」显式写进预期表。**诚实地记录不确定，比假装确定更专业。**

判定顺序按**证据强度**排，越不依赖主观预期的越先判：

| 顺序 | 判据 | 依赖预期吗 | 理由 |
|---|---|---|---|
| 1 | 500 | 完全不需要 | 任何用户输入都不该让服务崩 |
| 2 | 3xx | 不需要 | 出现就是 runner 配错了（没关重定向） |
| 3 | 4xx | 只需「该不该拒」 | 二分判断，简单 |
| 4 | 注入 | 不需要 | 载荷 + 结果集越界，双重证据 |
| 5 | 超集 / 交叉 | 不需要 | 纯集合事实 |
| 6 | 语义预期 | **需要** | 最软，放最后 |

这样最后落在主观判断上的争议最少。

### 6.6 第五层：横向一致性

前四层都是**纵向**的（一个参数位内部，变体 vs 基线）。这一层是**横向**的，而且**不需要预期**——这是它最大的价值。

**等价组检查**：语义相同、写法不同，结果必须一致。

```
month: '11月'=5条 / '11'=7条 / 'Nov'=7条 / 'nov'=7条 / '2026-11'=7条
type:  'Credit'=200/1条 / 'credit'=500 / 'CREDIT'=500
```

五种写法都表达「11 月」，给出两种结果 → **必然至少一个错**，跟 PRD 怎么写无关。

这类缺陷在第 4 层会被「预期写成两种都放行」豁免掉，只有横向摆在一起才暴露。

**跨接口检查**：同一个值在不同接口上是否被同等对待。

```
accountId=0 → tx_by_account=400 / 其余 4 个=200+空
```

单看每个接口都能自圆其说，横着摆才矛盾。

**为什么不需要预期**：因为「同一个语义给两种结果」本身就是矛盾，不需要知道哪种是对的。这是整个分析里证据最硬的一类结论。

### 6.7 第六层：落盘

10 列，核心是 `evidence`——必须写成**能直接贴进缺陷单**的句子：

```
注入载荷返回 200，结果集超集于基线（21 条 vs 基线 7 条），account_id 过滤被绕过
结果与基线逐条相同（7/7 条）—— 过滤条件根本没加进查询，但接口返回 200
返回 7 条，比基线多 2 条 —— 过滤条件被削弱（不是没生效，是生效错了方向）
```

对比「结果异常，请检查」——后者开发会问「哪里异常」。**证据的标准是：开发看完不需要再跑一遍就能定位。**

## 八、自检与常见误判

### 8.1 三个反向自检

工具本身必须能被证伪，否则它报「全部通过」你也不知道该不该信。

| 自检动作 | 预期结果 | 验证的能力 |
|---|---|---|
| 把 `onDate` 基线改成 0 条的值 | 只报 **1 条** `BASELINE_BROKEN`，不报 7 条假缺陷 | 根因收敛 |
| 把某条 case 的 `result_count` 改成 99 | 命中 **1 条** `DATA_INCONSISTENT` | 解析自洽检查 |
| 给值库加一个新值但不写预期 | 覆盖率显示 `93/94`，且报 `NO_EXPECTATION` | 漏判可见 |

三个都通过，才能相信「94 条变体、26 条命中、68 条通过」这个结论。

### 8.2 常见误判

| 现象 | 别急着判 | 先确认 |
|---|---|---|
| 返回 0 条 | 「参数被忽略」 | 基线是否非空？这天/这月库里是否真没数据？ |
| 返回全量 | 「过滤没生效」 | 变体结果是否**逐条相同**？还是恰好条数相同？ |
| 500 | 「服务有 bug」 | 是否 `Content-Type: text/html` 的容器错误页？请求是否根本没进业务层？ |
| 404 | 「参数值错了」 | 是路由没匹配（空值/双斜杠），还是类型转换失败，还是业务查不到？ |
| 条数一致 | 「结果一致」 | 比过 id 集合吗？ |

### 8.3 本方法的已知边界

**不查数据库对账。** 数据库只知道「数据是什么」，不知道「参数该不该生效」。`month=Nov` 返回 7 条，库里确实有 7 条，两者「一致」——但参数被静默忽略了。参照系必须是 baseline + 等价组 + 语义预期，不是 DB。

接口 vs SQL 的对账是**另一层测试**，要处理时区（接口比库早一天）和精度（`300.00` vs `300.0000`），不在本方法职责内。

**跨接口检查按 `kind` 归并，粒度偏粗。** `transactionId=0` 和 `accountId=0` 都被归到 `int`，要求「同等对待」有点勉强——这两个语义不同（不存在的交易 vs 不存在的账户）。当前设计换来的是「不用为每个参数位单独定义跨接口规则」。要收紧，得把桶的键从 `(kind, value)` 改成 `(kind, value, 语义角色)`。

**只适合有稳定数据快照的系统。** 数据一变，所有条数结论失效。真实项目里要配套数据准备脚本，或者在断言里只比较「集合关系」不比较「具体条数」。

## 九、这套方法移植到真实项目时的顺序

1. **拿接口清单**（OpenAPI / 网关路由 / 代码注解），确认参数位数量。
2. **造 baseline**，每个参数位一个，**必须实测非空**。
3. **写值库**，按类型归组，每类覆盖：合法边界、类型错、极值、空、特殊字符。
4. **跑矩阵**，先过 sanity check。
5. **写预期**，只写能确定的；不确定的写多个语义，不要猜。
6. **分析**，按六层顺序，先看闸门再看判定。
7. **提炼契约表**，事实与判断分列。
8. **写用例**，从契约表来，不要从矩阵来。

第 8 步是最容易被跳过、也最容易做错的一步：**矩阵是实验，用例是资产。** 106 条实验不该变成 106 条用例，该变成 40 条断言 + 一份契约表。
