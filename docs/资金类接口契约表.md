# ParaBank 资金类接口契约表（转账 / 存取款）

> 被测系统：ParaBank（本地部署，`http://localhost:8080/parabank`）
> 覆盖范围：3 个写接口（`/deposit`、`/withdraw`、`/transfer`）+ 2 个观测接口（`/accounts/{id}`、`/accounts/{id}/transactions`）+ 1 个重置接口
> 数据来源：25 条单发探测（`probe_write/out/write_matrix.csv`）+ 3 组并发（`concurrency.csv`）+ 源码确认 + 数据库对账
> 编制日期：2026-11-23

---

## 一、这份表与「流水查询契约表」的差别

流水查询那张表的主体是「返回结构」——你传一个参数，它回一批数据，契约就是「这批数据长什么样」。

写接口不一样，三处根本差异决定了表的结构：

| 维度 | 流水查询 | 资金类接口 |
|---|---|---|
| **结果在哪** | 响应体里（XML/JSON 数组） | **响应体里没有**。只有一句 `Successfully transferred $100 from ...` |
| **主体列** | 返回结构、字段类型 | **副作用**：余额变动、流水条数、借贷方向、描述文案 |
| **前置条件** | 基本无（只依赖账户存在） | **必须有**。同一笔 `-100` 在 10.45 的账户和 1100 的账户上是两件事 |

所以这份表的核心不是「返回什么」，而是「**做完之后，世界变成了什么样**」。

契约状态四档：

| 标记 | 含义 |
|---|---|
| ✅ | 行为合理，可直接写成断言 |
| ⚠️ | 行为确定，但是否合理待确认（文档没写、或多种设计都成立） |
| ❌ | 与通行契约明显冲突，用例应断言「正确行为」并标已知失败 |
| 🚫 | **测不出来**。观测手段本身失效，无法判定对错 |

第四档是这份表独有的——写接口能把自己的观测手段弄坏（见 4.1 的 D4）。

## 三、通用契约

### 3.1 响应形态：声明 JSON，实为裸文本

| 接口 | 状态 | `Content-Type` | body 原文 |
|---|---|---|---|
| `POST /deposit` | 200 | `application/json` | `Successfully deposited $100 to account #12456` |
| `POST /withdraw` | 200 | `application/json` | `Successfully withdrew $50 from account #12456` |
| `POST /transfer` | 200 | `application/json` | `Successfully transferred $100 from account #13122 to account #12567` |

**`Accept: application/json` 也不改变结果**，说明服务端忽略内容协商，`Content-Type` 是写死的。

后果：`resp.json()` 抛 `JSONDecodeError`。客户端如果按 JSON 解析，会把「转账成功」读成「解析失败」——这是 ❌ 契约缺陷（G9）。

响应体里**不含**：交易 ID、余额、状态码、时间戳、任何可用于对账的字段。

### 3.2 错误响应三层

| 层 | 触发 | 状态 | `Content-Type` | body | 长度 |
|---|---|---|---|---|---|
| **路由/类型转换** | `accountId=abc`、`1.5`、溢出 | **404** | 无 | 空 | 0 |
| **业务校验** | 账户不存在（`0`、`99999`） | **400** | `text/plain` | `Could not find account number 0` | 31 |
| | `transfer` 任一账户不存在 | **400** | `text/plain` | `Could not find account number 13122 and/or 99999` | 48 |
| **未捕获异常** | 缺 `amount` 参数 | **500** | `text/html` | Tomcat 错误页 | 4264 |
| | `amount=`（空串） | **500** | `text/html` | Tomcat 错误页 | 3296 |

三层对应三种完全不同的处置：404 说明**请求没进业务代码**，400 说明**进了但被拒绝**，500 说明**进了但没人拦**。

两个不对称，值得单独记：

| 现象 | 结果 | 说明 |
|---|---|---|
| 缺 `accountId` | **400**（不是 500） | 缺失的 int 被当成 `0`，走了业务校验 `Could not find account number 0` |
| 缺 `amount` | **500** | 缺失的 `BigDecimal` 在拆箱时 NPE |

**同样是「缺参」，一个 400 一个 500**，说明参数校验没有统一入口（G8）。

### 3.3 唯一的判据：写后回查

因为响应体不承载结果，所有断言必须建立在操作前后的状态差上：

| 观测点 | 怎么取 | 陷阱 |
|---|---|---|
| 余额 | `GET /accounts/{id}` → `balance` | 余额出现 3 位小数时，此接口**永久 500**，观测手段本身失效 |
| 流水 | `GET /accounts/{id}/transactions` | 必须取 **ID 集合差**，不能取条数差（否则不知道新增的是哪条、金额多少） |
| 响应体 | `POST` 的返回文本 | 只能用于断言「成功/失败」，不能用于对账 |

### 3.4 时间与精度

**金额精度**：

| 层 | 精度 | 实测样例 |
|---|---|---|
| 数据库 `AMOUNT` / `BALANCE` | `DECIMAL(…,4)` | `300.0000`、`10.4500` |
| 接口 JSON | 2 位（`double`，去尾零） | `300.0`、`10.45`、`-2300.0` |

**接口返回的是 JSON 数字，不是字符串**，尾零会被去掉。断言不能做字符串比较——`"-2300.0" != "-2300.00"`。

**日期语义**（这一项容易误判，单独说明）：

| 层 | 表示 | 实测（库中 `2026-11-12`） |
|---|---|---|
| 数据库 `DATE` | 日期，无时区 | `2026-11-12` |
| JSON `date` | **epoch 毫秒**，表示本地零点 | `1794412800000` → `2026-11-12T00:00:00+08:00` |
| XML `date` | 同一时刻的 **UTC** 字符串 | `2026-11-11T16:00:00.000Z` |

**epoch 是正确的，XML 字符串也没有错——错的是「按 UTC 解读它」这个动作。** 本地零点在 UTC 下就是前一天 16:00。断言日期时要按 UTC+8 还原，不要直接把字符串截前 10 位。

## 四、三个接口逐个契约

### 4.1 `POST /deposit`

**参数**（全部在 **query string**，不是 JSON body）：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `accountId` | int | 是 | 收款账户 |
| `amount` | decimal | 是 | 存入金额，**无符号校验** |

**正常副作用**（D1：`accountId=12456`，`amount=100`）：

| 项 | 实测 |
|---|---|
| 响应 | 200 `Successfully deposited $100 to account #12456` |
| 余额 | `10.45` → **`110.45`** |
| 新增流水 | 1 条 `Credit 100.00` |
| 描述文案 | `Deposit via Web Service` |

**边界与非法值**：

| # | 输入 | 状态 | 余额变动 | 新增流水 | 契约状态 |
|---|---|---|---|---|---|
| D1 | `100` | 200 | `+100.00` | 1 条 Credit 100.00 | ✅ |
| D2 | `-100` | 200 | **`-100.00`** | 1 条 Credit **-100.00** | ❌ 存款传负数变成扣款（G1） |
| D3 | `0` | 200 | `0.00` | 1 条 Credit 0.00 | ❌ 零元也生成流水（G2） |
| D4 | `0.001` | 200 | **读不到（N/A）** | **无法观测** | ❌ **账户被打坏**（G3） |
| D5 | `999999999` | 200 | `+999999999.00` | 1 条 | ❌ 无上限（G4） |
| D6 | `accountId=0` | 400 | 0 | 0 | ✅ |
| D7 | 缺 `amount` | 500 | 0 | 0 | ❌ 缺参应 400（G8） |

D4 的细节：返回 **200 成功**，之后 `GET /accounts/12456` 和 `/transactions` **双双 500**，只有 `initializeDB` 能恢复。原因见 G3。

### 4.2 `POST /withdraw`

参数同 deposit（`accountId`、`amount`），语义相反。

**正常副作用**（W1：`accountId=12456`，`amount=50`）：

| 项 | 实测 |
|---|---|
| 响应 | 200 `Successfully withdrew $50 from account #12456` |
| 余额 | `10.45` → **`-39.55`**（已经透支，仍返回成功） |
| 新增流水 | 1 条 `Debit 50.00` |
| 描述文案 | `Withdraw via Web Service` |

**边界与非法值**：

| # | 输入 | 状态 | 余额变动 | 新增流水 | 契约状态 |
|---|---|---|---|---|---|
| W1 | `50` | 200 | `-50.00` | 1 条 Debit 50.00 | ✅ |
| W2 | `-100` | 200 | **`+100.00`** | 1 条 Debit **-100.00** | ❌ 取款传负数变成存钱（G1） |
| W3 | `0` | 200 | `0.00` | 1 条 Debit 0.00 | ❌ 零元也生成流水（G2） |
| W4 | `0.001` | 200 | 读不到（N/A） | **无法观测** | ❌ 账户被打坏（G3） |
| W5 | `accountId=12900`（0.00）`amount=100` | 200 | **`-100.00`** | 1 条 Debit 100.00 | ⚠️ 允许透支，需产品决策（G5） |
| W6 | `accountId` 不存在 | 400 | 0 | 0 | ✅ |
| W7 | 缺 `amount` | 500 | 0 | 0 | ❌ 缺参应 400（G8） |

### 4.3 `POST /transfer`

**参数**（query string，三个）：

| 参数 | 类型 | 必填 |
|---|---|---|
| `fromAccountId` | int | 是 |
| `toAccountId` | int | 是 |
| `amount` | decimal | 是 |

**实现结构**（`BankManagerImpl.transfer`）：

```java
public void transfer(int from, int to, BigDecimal amount) {
    withdraw(from, amount, "Funds Transfer Sent");      // 先扣
    deposit(to, amount, "Funds Transfer Received");     // 后加
}
```

先扣后加，整个方法被 AOP 事务包裹（`applicationContext-base.xml:203-211`，切入点 `BankManager.*`）。

**正常副作用**（T1：`13122 → 12567`，`amount=100`）：

| 账户 | 余额 | 新增流水 | 描述 |
|---|---|---|---|
| 13122（付方） | `1100.00` → **`1000.00`** | 1 条 `Debit 100.00` | `Funds Transfer Sent` |
| 12567（收方） | `100.00` → **`200.00`** | 1 条 `Credit 100.00` | `Funds Transfer Received` |

付方流水 ID（`14476`）< 收方流水 ID（`14587`），与「先扣后加」一致。

**边界与非法值**：

| # | 场景 | 状态 | Δ付方 | Δ收方 | 流水 | 契约状态 |
|---|---|---|---|---|---|---|
| T1 | 正常 100 | 200 | `-100` | `+100` | 1 + 1，守恒 | ✅ |
| T2 | `amount=-100` | 200 | **`+100`** | **`-100`** | 1 + 1，守恒 | ❌ 方向反转（G1） |
| T3 | `amount=0` | 200 | `0` | `0` | **2 条**净零 | ❌ 零元也生成流水（G2） |
| T5 | 零余额账户转出 100 | 200 | `-100` | `+100` | 1 + 1 | ⚠️ 允许透支（G5） |
| T6 | `to` 不存在 | **400** | **`0`** | — | **0 条** | ✅ **事务回滚生效** |
| T7 | `from` 不存在 | **400** | `0` | — | 0 条 | ✅ 同上 |
| T8 | `from == to` | 200 | `0` | — | **2 条**（Debit 100 + Credit 100） | ❌ 自己转自己生成两条流水（G7） |
| T9 | 跨客户（13455） | 200 | `-100` | `+100` | 1 + 1 | ⚠️ 无客户校验，需确认（G10） |
| T4 | `amount=0.001` | 200 | 读不到 | 读不到 | **无法观测** | ❌ 双方账户都被打坏（G3） |

**T6/T7 是这张表里唯一一条「好消息」**：`withdraw` 已经扣了钱，`deposit` 抛 `DataAccessException`，事务回滚把扣款撤销，余额与流水都回到原状。

它同时确定了一件事：**原子性不需要再测，要测的是事务管不到的部分——并发与幂等。**

## 五、参数级横向汇总

同一个值丢进三个接口，行为是否一致：

| 输入 | `/deposit` | `/withdraw` | `/transfer` | 一致？ |
|---|---|---|---|---|
| `amount=-100` | 余额 **-100**（变扣款） | 余额 **+100**（变加钱） | **方向反转** | ❌ 三个都错，但错法各异 |
| `amount=0` | 流水 +1，余额不动 | 流水 +1，余额不动 | 流水 +2，余额不动 | ✅ 行为一致（都错） |
| `amount=0.001` | 200，账户坏 | 200，账户坏 | 200，双方坏 | ✅ 行为一致 |
| `amount` 缺失 | 500 | 500 | 500 | ✅ 行为一致 |
| `accountId` 缺失 | 400（当 0 处理） | 400 | 400（`0 and/or x`） | ✅ 行为一致 |
| `accountId=abc` | 404 | 404 | 404 | ✅ 行为一致 |
| 账户不存在 | 400 | 400 | 400 | ✅ 行为一致 |

**一个必须记下来的副产物**：负数金额时，流水记录的 `type` 字段**不翻转**，只有金额变负。

```
deposit -100  →  type=Credit, amount=-100.00
withdraw -100 →  type=Debit,  amount=-100.00
```

这意味着「按 type 汇总」和「按金额汇总」会得到相反结论：报表按 `type=Credit` 求和会把它算成存款（实际是扣款）；按金额求和则是对的。**同一份数据，两种口径，两个答案。**

## 六、并发行为（实现属性，不属于接口契约）

3 组，付方 12456（余额 10.45），收方 12567：

| 规模 | 应扣 | 实扣 | 收方到账 | 守恒 | 流水条数 |
|---|---:|---:|---:|---|---|
| 10 × 10 元 | -100 | **-40** | +100 | ❌ 凭空多 60 | 10 / 10 ✅ |
| 20 × 5 元 | -100 | **-25** | +100 | ❌ 凭空多 75 | 20 / 20 ✅ |
| 30 × 1 元 | -30 | **-5** | +30 | ❌ 凭空多 25 | 30 / 30 ✅ |

三个事实：

1. **流水条数全部正确**，只有余额错。所以「比对流水条数」这个校验手段在并发场景下**完全失效**。
2. **收款方每次都足额到账，付款方每次都少扣**，差额就是「凭空多出来的钱」。
3. **丢失量不稳定**：同一场景（10 × 10）两次跑分别得到 `-50` 和 `-40`。这不是测试不稳定，**竞态的定义就是不收敛**。

根因链：

```
transfer = withdraw + deposit          → 两个方法在同一事务内，原子性有保证
withdraw = getAccount() → debit(内存) → updateAccount()
updateAccount: UPDATE Account SET balance = :balance    → 绝对值赋值，不是 balance = balance - ?
```

两个请求同时读到 `-2300`，各自算出 `-2310` 并写回，后写的覆盖先写的——**丢失更新**。事务只保证「一个事务的修改整体生效或整体回滚」，不保证「两个事务不会同时读到同一个旧值」。

> **用例层已消除这个混杂**：`tests/test_transfer.py::TestConcurrency` 的付款方改用 13122（1100.00），
> 10 × 10 元实测 Δ = **-30.00**（应 -100），凭空多出 70，流水仍是 10 / 10 条全对。
> 1100 足够扣 110 次，所以「余额不足」不再是候选解释 —— `Δ ≠ -100` 只可能是丢失更新。
>
> 上表三组的数字是**探测阶段**（付方 12456）的记录，保留原样用于对照：
> 同一场景四次跑得 -50 / -40 / -25 / -30，量级不收敛，这是竞态本身的性质。

## 七、契约缺口清单

按**根因**归并，同一根因的多个 case 只算一条：

| 编号 | 缺口 | 证据 | 性质 | 影响 |
|---|---|---|---|---|
| **G1** | 负数金额不校验，方向反转 | D2 W2 T2 | ❌ 缺陷 | 转账方向被反向利用；流水 `type` 与金额符号矛盾 |
| **G2** | 零金额仍生成流水 | D3 W3 T3 T8 | ❌ 缺陷 | 制造噪音流水，污染按条数统计的对账 |
| **G3** | 3 位小数使账户永久不可读（P0） | D4 W4 T4 | ❌ 缺陷 | 一次非法输入换来账户永久 500，只能 reset |
| **G4** | 金额无上限 | D5 | ❌ 缺陷 | 可一次性写入 10 亿，无风控 |
| **G5** | 允许无限透支 | W5 T5 | ⚠️ 空白 | 零余额可转出 100；是否有额度策略文档未说明 |
| **G6** | 无幂等 | I1 I2 | ⚠️ 空白 | 同参数连发 2 次扣 2 次；接口无幂等键，服务端无从去重 |
| **G7** | 自己转自己生成 2 条净零流水 | T8 | ❌ 缺陷 | 应拒绝或至少不产生流水 |
| **G8** | 缺参 / 空参 → 500 而非 400 | D7 W7 | ❌ 缺陷 | 客户端错误被当成服务端错误；缺 `accountId` 却返回 400，校验层次不统一 |
| **G9** | 响应声明 JSON 实为裸文本 | 三个接口 | ❌ 缺陷 | `resp.json()` 抛异常，标准客户端无法解析 |
| **G10** | 跨客户转账无校验 | T9 | ⚠️ 空白 | 客户 12212 可向 12323 转账，是否需要授权未说明 |

三条 ⚠️ 是**契约空白，不是缺陷**：文档没说清、单看每个接口都能自圆其说。处置方式是「先问预期」，不是提单。

**G3 的根因**（已定位到代码）：

```java
// JdbcAccountDao.java:29 —— 读路径
balance.setScale(2);                       // 没有 RoundingMode
// → 余额出现第 3 位小数时，抛 ArithmeticException: Rounding necessary
```

写路径不校验精度照样入库，读路径却假设「精度一定 ≤ 2 位」。**契约在这里断裂：写的时候允许，读的时候崩。**

|---|---|---|
| 4.1 / 4.2 / 4.3 的「正常副作用」 | 正向用例 + **对账断言** | 5 |
| 五、横向汇总里的 7 个输入 | 参数矩阵（一个值测三个接口） | 12 |
| 3.2 错误分层三层 | 错误响应契约 | 6 |
| 4.1–4.3 的 ❌ 行（G1–G4、G7、G8） | `xfail(strict=True)` 固化缺陷 | 7 |
| 六、并发 3 组 | `-m concurrency`，**默认不进回归** | 3 |
| G6 幂等 | xfail，注明「缺幂等键，需产品决策」 | 2 |

**每次写操作之后都必须跑的四条对账**（不是独立接口，是一组断言）：

```
① 借贷守恒   ΔA + ΔC = 0
② 扣款到位   ΔA = -amount × 次数
③ 流水对账   新增流水金额之和 = |ΔA|
④ 类型正确   A 侧 Debit、C 侧 Credit
```

②③ 是两条独立路径——一条对不代表数据对。这和流水查询里「`result_count` vs `result_ids`」是同一个思想。

**不要做的**：把 25 条探测原样搬成 25 条用例。`amount=100` 和 `amount=200` 没有本质差别，值得固化的只有「正常、边界、非法」三类各一个代表。

### 落地情况（`tests/test_transfer.py`）

| 组 | 条数 | 覆盖 | marker |
|---|---:|---|---|
| 正常路径 | 7 | 存款/取款/转账的副作用、守恒、流水对账、零余额收款、跨账户类型 | `happy` |
| 响应契约 | 4 | 成功文案、G9 伪装 JSON、400 text/plain、404 空 body | `contract` |
| 参数校验 | 16 | 404（accountId/amount 不可解析）、400（账户不存在）、500（缺参/空参）、科学计数法 | `validation` |
| 金额语义 | 10 | 负数 ×3、零 ×3、精度、10 亿、透支 ×2 | `boundary` |
| 原子性 / 转账特化 | 5 | 两个方向回滚、自转自、跨客户、双方精度损坏 | `consistency` |
| 幂等 | 2 | 转账 / 存款各连发 2 次 | `consistency` |
| 并发 | 2 | 丢失更新、流水条数对但余额错 | `concurrency` |
| **合计** | **46**（33 个函数） | 其中 **21 条 xfail**，对应 G1–G10 | |

比预估的 35 条多，多出来的两处是**这次写用例时才发现**的：

1. **`amount=1.5` 是合法的** —— 写接口的 `amount` 是 `BigDecimal`，而流水查询的 `amount` 是 `int`。同一套「非法值」清单不能跨模块复用。
2. **`amount=1e3` 被解析成 1000** —— 金额格式比直觉宽松，客户端不该假设只有 `\d+(\.\d+)?`。这条单独固化成用例，防止哪天拿正则校验金额的客户端代码被这个事实打脸。

## 九、已知局限

| 局限 | 说明 |
|---|---|
| 观测层单通道 | 余额与流水都来自 REST 接口，没有内建 DB 交叉验证（手工验过一次：并发场景两条通道数字一致） |
| 并发付方透支混杂 | 见第六节末尾 |
| 未测：超 long 范围金额 | `99999999999999999999` 这类输入未验证，可能落到 404 或 500 |
| 未测：金额含空格/逗号 | `"100 "`、`"1,000"` 的解析行为未知 |
| 未测：`amount` 为多个值时 | 如 `amount=100&amount=200`，取第一个还是报错未知 |
| 未测：新建账户是否被 reset 清掉 | 见 2.2 |
| `transfer` 中途失败的第三种形态 | 只测了「账户不存在」。「扣款成功后进程崩溃」这类无法通过 API 构造 |
