# ParaBank 流水查询接口契约表

> 被测系统：ParaBank（本地部署，`http://localhost:8080/parabank`）
> 覆盖范围：流水查询相关 6 个 GET 接口
> 数据来源：106 条探测矩阵（`probe/out/matrix.csv`）+ 源码确认 + 数据库对账
> 编制日期：2026-11-21

---

## 一、这份表记录什么

契约 = **接口对外承诺的可观测行为**。它回答的是「我传这个值，你会怎么回应」，不是「你的代码怎么写的」。

三条编制原则：

1. **只写实测过的**。每一条结论要么能指回 `matrix.csv` 的 case_id，要么能指回一条 curl 命令。没测过的不写，测不出来的标「待验证」。
2. **事实与判断分列**。「实测行为」是客观记录，「契约状态」是主观判断。两者混在一起，表就会变成意见清单。
3. **记录环境**。时区、数据快照、字符集不写清楚，别人拿到表也复现不出来。

「契约状态」只有三档：

| 标记 | 含义 |
|---|---|
| ✅ | 行为合理，可直接写成断言 |
| ⚠️ | 行为确定，但是否合理待确认（文档没写、或多种设计都成立） |
| ❌ | 行为与通行契约明显冲突，写用例时应断言「正确行为」并标记为已知失败 |

### 账户 12345 的 7 条流水

**日期是相对 `CURRENT_DATE` 生成的，每次 `initializeDB` 都会变**（`insert.sql:44-60`）。
所以这里记录的是「日期怎么算出来的」，不是固定值：

| ID | TYPE | 日期生成规则 | AMOUNT | 说明 |
|---|---|---|---|---|
| 12145 | 0 = Credit | `YEAR(CURRENT_DATE - 1 YEAR)-12-11` | 300.0000 | 去年 12 月，月份固定 |
| 12256 | 1 = Debit | `YEAR(CURRENT_DATE - 1 YEAR)-12-12` | 100.0000 | 去年 12 月，月份固定 |
| 12589 | 1 = Debit | `CURRENT_DATE - 15 DAY` | 1000.0000 | |
| 13255 | 1 = Debit | `CURRENT_DATE - 11 DAY` | 100.0000 | 与 13477 同日 |
| 13477 | 1 = Debit | `CURRENT_DATE - 11 DAY` | 1000.0000 | 与 13255 同日 |
| 13699 | 1 = Debit | `CURRENT_DATE - 10 DAY` | 0.0000 | 全库唯一零元流水 |
| 14143 | 1 = Debit | `CURRENT_DATE - 8 DAY` | 1000.0000 | 最近一条 |

以 **2026-11-21** 为基准日，实际落在
`2025-12-11 / 2025-12-12 / 2026-11-06 / 2026-11-10 / 2026-11-10 / 2026-11-11 / 2026-11-13`。

**哪些结论稳定、哪些会漂**：

| 稳定（可写死断言） | 会漂（必须动态算） |
|---|---|
| 总条数 7 | 任何具体日期 |
| ID 集合（种子写死） | 哪个月恰好有 5 条 |
| Credit 仅 12145 一条 | `onDate` 某天返回几条 |
| 去年 12 月恒有 2 条 | 日期范围查询的边界值 |
| 12456 / 12567 零流水 | |

> ⚠️ 写用例时**不要硬编码日期**。本文档下文出现的具体日期，都是 11-21 快照下的举例。
> 正确的做法是从接口返回的 epoch 反推日期（注意按 UTC+8 还原），用它构造参数。
>
> `TYPE` 在库里是数字：`0 = Credit`、`1 = Debit`。

## 三、通用契约（6 个接口共有）

### 3.1 返回结构

| 场景 | 根标签 | 示例 |
|---|---|---|
| 单条查询（`/transactions/{id}`） | `<transaction>` | 裸对象，**不包数组** |
| 列表查询（其余 5 个） | `<transactions>` | 内含 N 个 `<transaction>` |
| 列表查询返回 0 条 | `<transactions></transactions>` | 空容器，**不是 404** |

单条响应示例：

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<transaction>
  <id>12145</id>
  <accountId>12345</accountId>
  <type>Credit</type>
  <date>2025-12-10T16:00:00.000Z</date>
  <amount>300.00</amount>
  <description>Check # 1111</description>
</transaction>
```

列表响应示例：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<transactions>
  <transaction>...</transaction>
  <transaction>...</transaction>
</transactions>
```

> 注意两个差异：单条的 XML 声明带 `standalone="yes"`，列表不带；列表空结果是一个**空容器**（67 字节），不是空 body。

### 3.2 内容协商

| `Accept` 头 | 响应格式 | `date` 字段形态 | `amount` 字段形态 |
|---|---|---|---|
| 默认 / `application/xml` | XML | `2025-12-10T16:00:00.000Z`（字符串） | `300.00`（字符串） |
| `application/json` | JSON | `1765382400000`（epoch 毫秒） | `300.00`（数字） |

JSON 实测响应：

```json
{"id":12145,"accountId":12345,"type":"Credit","date":1765382400000,"amount":300.00,"description":"Check # 1111"}
```

> 同一条记录，XML 给的是格式化字符串，JSON 给的是 epoch 毫秒。**写断言时两种格式不能共用同一套比较逻辑**，否则日期一定对不上。

### 3.3 排序

**`ORDER BY date, id`**（`JdbcTransactionDao.java:114`），不是按 id 排。

实测 7 条返回顺序：`12145(12-11) → 12256(12-12) → 12589(11-05) → 13255(11-09) → 13477(11-09) → 13699(11-10) → 14143(11-12)`，与日期升序完全一致；两个同日记录（13255/13477）按 id 升序。

✅ 可直接断言：任何列表接口的结果都按 `(date, id)` 升序。

### 3.4 时区

| 层 | 值（11-21 快照） |
|---|---|
| 数据库 `DATE` | `2026-11-05`（日期，无时区） |
| 接口返回 | `2026-11-04T16:00:00.000Z` |
| 换算 | `2026-11-04 16:00 UTC` = `2026-11-05 00:00 UTC+8` |

**同一时刻，但字符串上比库里的日期小一天。**

推导依据：7 条记录全部稳定偏移 8 小时，且偏移方向与 UTC+8 一致（`14143` 库内 `11-12` → 接口 `11-11T16:00Z`）。

> ⚠️ 这是最容易踩的坑：拿接口返回的 `date` 直接和库里的 `DATE` 做字符串相等比较，**永远失败**。
> 正确做法：把 epoch 转成 `UTC+8` 再取日期部分，或者两边都转 epoch 比较。

### 3.5 金额精度

| 层 | 值 |
|---|---|
| 数据库 `DECIMAL` | `300.0000`（4 位小数） |
| XML 返回 | `300.00`（2 位小数） |
| JSON 返回 | `300.00`（数字，2 位） |

> ⚠️ **输出侧存在精度收窄**（4 位 → 2 位）。
> 现有样本的小数位恰好都是 `.xx00`，无法区分是四舍五入还是截断，标为**待验证**。
> 输入侧不受影响：`amount=100.0000` 能精确匹配库里的 `100.0000`，说明 SQL 比较走的是数值语义，不是字符串（见 5.3）。

### 3.6 错误响应分层

同样是「请求失败」，系统在三个不同层面拒绝，响应完全不同。**这是本表最需要记住的一张表**：

| 层 | 触发条件 | 状态码 | `Content-Type` | Body |
|---|---|---|---|---|
| A. 路由 / 参数转换 | int 参数非数字、小数、溢出、空值 | **404** | *（无）* | **0 字节** |
| B. 业务校验 | ID 能解析，但对应记录不存在 | **400** | `text/plain;charset=UTF-8` | `Could not find transactions for account #0`（29–44 字节） |
| C. 服务端异常 | 值拼进 SQL 后类型/语法错误 | **500** | `text/html` | Tomcat 错误页，4264 字节 |

实测样本：

| case | 请求 | 状态 | 响应 |
|---|---|---|---|
| C005 | `transactionId=abc` | 404 | 空 body |
| C016 | `accountId=`（空） | 404 | 空 body（双斜杠导致路由不匹配） |
| C017 | `accountId=2147483648` | 404 | 空 body（超出 int 范围） |
| C002 | `transactionId=0` | 400 | `Could not find transaction #0` |
| C011 | `accountId=0` | 400 | `Could not find transactions for account #0` |
| C060 | `type=CREDIT` | 500 | Tomcat 错误页 |

> **404 和 400 的区别不是「参数错」和「记录不存在」这么简单**：
> 404 发生在**进 Java 方法之前**（路由匹配失败 / 参数类型转换失败），此时业务代码一行都没执行；
> 400 是业务代码主动抛出的（`ParaBankServiceException`）。
> 排查时看 `Content-Type` 最快：空 + 0 字节 = 没进业务层；`text/plain` = 业务层主动拒绝；`text/html` = 业务层崩了。

## 四、接口逐个契约

### 4.1 按流水 ID 查单条

```
GET /services/bank/transactions/{transactionId}
```

返回**单个** `<transaction>`，不是数组。

| 参数 | 类型 | 格式 | 合法值实测 | 非法 / 边界值实测 | 状态 |
|---|---|---|---|---|---|
| `transactionId` | int | 十进制整数 | `12145` → 200 / 1 条 | `0`/`-1`/`1` → 400；`abc`/`1.5`/空/`2147483648`/`1 or 1=1` → 404 | ✅ |

> `0`、`-1`、`1` 都能被解析成 int，所以进到了业务层，业务层查不到 → 400。
> `abc` 这类转不了 int，在路由层就被挡下 → 404。
> **同样是「不存在的 ID」，走的是两条完全不同的错误路径。**

---

### 4.2 按账户查全部流水

```
GET /services/bank/accounts/{accountId}/transactions
```

| 参数 | 类型 | 格式 | 合法值实测 | 非法 / 边界值实测 | 状态 |
|---|---|---|---|---|---|
| `accountId` | int | 十进制整数 | `12345` → 200 / 7 条 | `0`/`-1`/`1` → **400**；`abc`/`1.5`/空/溢出/注入 → 404 | ✅ |

> 本接口是 5 个列表接口中**唯一**对「账户不存在」返回 400 的（因为它多调了一次 `getAccount` 校验）。其余 4 个一律返回 200 + 空。详见 6.4。

---

### 4.3 按金额查

```
GET /services/bank/accounts/{accountId}/transactions/amount/{amount}
```

| 参数 | 类型 | 格式 | 合法值实测 | 非法 / 边界值实测 | 状态 |
|---|---|---|---|---|---|
| `accountId` | int | 十进制整数 | `12345` → 200 / 1 条 | `0`/`-1`/`1` → **200 / 0 条**（无校验）；`abc` 等 → 404 | ⚠️ 与 4.2 不一致 |
| `amount` | BigDecimal | 十进制，支持科学计数法 | `300` → 1 条（12145）；`0` → 1 条（13699） | `-100` → 200/0；`99` → 200/0；`abc`/空 → 404 | ✅ |

金额参数的语义是**精确等值匹配**，不是范围。实测证据：

| 输入 | 结果 | 说明 |
|---|---|---|
| `300` | 1 条（12145） | 匹配库里 `300.0000` |
| `300.00` | 1 条（12145） | 与 `300` **结果完全相同** → 数值语义，不是字符串匹配 |
| `100.0000` | 2 条（12256, 13255） | scale 不同但值相同，能匹配上 |
| `0` | 1 条（13699） | 库里真有一条 `0.0000` 的流水，不是「空查询」 |
| `1e10` | 0 条 | 科学计数法被 `BigDecimal` 接受，不是格式错误 |
| `-100` | 0 条 | 负数被接受，只是无匹配 |

> ⚠️ `amount=0` 返回 1 条而不是 0 条，**容易误判成「参数没生效」**。要结合基线（`accountId=12345` 时有 7 条）才能确认它确实过滤了。

---

### 4.4 按月份 + 类型查

```
GET /services/bank/accounts/{accountId}/transactions/month/{month}/type/{type}
```

这是 6 个接口里行为最偏离常规的一个。

#### `month` 参数

> 下表条数是 11-21 快照下的值。`month` 的结果**完全取决于运行日期**——最近 5 条流水
> 落在哪个月，哪个月就多出 5 条。
> 真正稳定的只有两条：`All` 恒等于全量；`12月` 恒包含 12145 / 12256（去年 12 月那两条）。

| 输入 | 结果 | 说明 | 状态 |
|---|---|---|---|
| `All` | 200 / 7 条 | 魔法值，表示不过滤 | ✅ |
| `11月` | 200 / 5 条 | 唯一被识别的 11 月写法 | ✅ |
| `12月` | 200 / 2 条 | 匹配到的是 **2025 年**的 12 月 | ⚠️ 见下 |
| `11` | 200 / **7 条** | 静默返回全量 | ❌ |
| `Nov` | 200 / **7 条** | 静默返回全量 | ❌ |
| `nov` | 200 / **7 条** | 静默返回全量 | ❌ |
| `2026-11` | 200 / **7 条** | 静默返回全量 | ❌ |
| `'` | 200 / **7 条** | 静默返回全量 | ❌ |
| 空值 | 404 | 双斜杠，路由不匹配 | — |

**格式契约**：只认中文月份缩写 `N月`（`SimpleDateFormat("MMM")` + JVM 默认 locale `zh_CN`）。

**比较契约**：`AND MONTH(date) = ?`，**只比月份，忽略年份**。
证据：`12月` 返回的 2 条是 `2025-12-11` / `2025-12-12`，而库里 2026 年 12 月没有数据。这说明它没有把年份纳入条件。

> ⚠️ 参数无法识别时，**不报错、不返回空，而是把过滤条件整个丢掉**，返回全量。
> 调用方看到 `200 + 7 条`，会以为「11 月真的有 7 条流水」，实际是「过滤没生效」。
> 这是本模块危害最大的一个行为：**错误的结果看起来像正确的结果**。

#### `type` 参数

| 输入 | 结果 | 说明 | 状态 |
|---|---|---|---|
| `All` | 200 / 7 条 | 魔法值，不过滤 | ✅ |
| `Credit` | 200 / 1 条（12145） | 映射为 `TYPE = '0'` | ✅ |
| `Debit` | 200 / 6 条 | 映射为 `TYPE = '1'` | ✅ |
| `CREDIT` | **500** | 大小写敏感，未命中枚举后原样拼入 SQL | ❌ |
| `credit` | **500** | 同上 | ❌ |
| `'` | **500** | 单引号拼进 SQL，语法错误 | ❌ |
| `0' OR '1'='1` | 200 / **21 条** | 绕过 `account_id` 过滤，返回全表 | ❌ |
| 空值 | 404 | 路由不匹配 | — |

**取值契约**：仅 `Credit` / `Debit` / `All`，**首字母大写**。

**根因**（`JdbcTransactionQueryRestrictor.java:24-31`）：枚举匹配失败时不做校验，把原始字符串直接拼进 SQL：

```java
type = Integer.toString(TransactionType.valueOf(type).ordinal());
} catch (IllegalArgumentException e) {
    // just pass it along so we can introduce SQL injection vulnerabilities
}
restrictionsSql += " AND TYPE = '" + type + "'";
```

`TYPE` 是整数列，拿 `'CREDIT'` 比较 → HSQLDB 类型转换异常 → 500。
`0' OR '1'='1` 拼成 `AND TYPE = '0' OR '1'='1'` → 条件恒真 → 21 条全表。

> ❌ 两件事同时成立：**输入校验缺失**（非法值导致 500）+ **SQL 注入**（值被当代码执行）。
> 源码注释写明这是「故意引入的注入漏洞」，属于演示项目的教学桩，但行为本身仍是缺陷。

### 4.5 按日期范围查

```
GET /services/bank/accounts/{accountId}/transactions/fromDate/{fromDate}/toDate/{toDate}
```

**格式契约**：`MM-dd-yyyy`（月-日-年，非 ISO）。

> 下表中的条数均为 **11-21 快照**下的值。日期每天漂移，换一天跑这些具体数字都会变，
> 但「非法日期不报错」这个行为不变。

| 参数 | 类型 | 格式 | 合法值实测 | 非法 / 边界值实测 | 状态 |
|---|---|---|---|---|---|
| `fromDate` | Date | `MM-dd-yyyy` | `11-01-2026` → 5 条 | `11-11-2026` → 1 条；`01-01-2026` → 5 条（全含） | ✅ |
| `toDate` | Date | `MM-dd-yyyy` | `11-30-2026` → 5 条 | `11-11-2026` → 4 条；`01-01-2026` → 0 条 | ✅ |

**边界语义**：两端都**闭区间**。`date >= fromDate AND date <= toDate`（源码 61-66 行）。

#### 非法日期的实测行为（lenient 解析）

`SimpleDateFormat` 默认 `setLenient(true)`，非法日期不会被拒绝，而是被「归一化」成另一个合法日期，然后照常参与查询：

| 输入 | 实际解析成 | fromDate 结果 | toDate 结果 |
|---|---|---|---|
| `13-45-2026` | **2027-02-14** | 0 条 | 5 条 |
| `02-30-2026` | **2026-03-02** | 5 条 | 0 条 |
| `00-00-0000` | **0002-11-30** | 7 条（全量） | 0 条 |
| `2026-11-11` | **0179-10-11** | 7 条（全量） | 0 条 |

（解析结果由 `SimpleDateFormat` 单测确认，非推测。）

> ❌ **没有任何一个非法日期返回 4xx。**
> `2026-11-11` 看起来「像 ISO 日期」，能被解析成公元 179 年，于是 `fromDate` 的下界被拉到公元前，返回**比基线更多的 7 条**——这就是「超集」缺陷的典型形态：条件生效了，但方向错了。

**方向契约**：`fromDate > toDate` 不报错，返回 200 + 0 条（由 SQL 条件自然成立）。

### 4.6 按单日查

```
GET /services/bank/accounts/{accountId}/transactions/onDate/{onDate}
```

**格式契约**：`MM-dd-yyyy`，与 4.5 相同。

| 参数 | 类型 | 格式 | 合法值实测 | 非法 / 边界值实测 | 状态 |
|---|---|---|---|---|---|
| `onDate` | Date | `MM-dd-yyyy` | 传某条流水的当天日期 → 命中该条 | `11-11-2026` → 200 / 0 条（当天确实无数据） | ✅ |
| | | | | `2026-11-11`/`13-45-2026`/`02-30-2026`/`00-00-0000` → 200 / 0 条 | ❌ |

**比较契约**：等值匹配 `date = ?`，与 4.5 的区间匹配分开实现。

> ❌ 非法日期同样不报错，只是「解析成远古日期后查不到」，返回 0 条。
> **注意这里的 0 条是「假阴性」**：调用方无法区分「那天没交易」和「你的日期格式我理解错了」。

## 五、参数级契约汇总

把 6 个接口的同类参数横向对齐。同一列出现不同行为的地方，用 ⚠️ 标出。

### 5.1 `accountId`（int）

| 接口 | `12345` | `0`（可解析但不存在） | `abc`（不可解析） | 空值 |
|---|---|---|---|---|
| 4.2 `/transactions` | 200 / 7 | **400** | 404 | 404 |
| 4.3 `/amount` | 200 / 1 | 200 / 0 | 404 | 404 |
| 4.4 `/month/type` | 200 / 7 | 200 / 0 | 404 | 404 |
| 4.5 `/fromDate/toDate` | 200 / 5 | 200 / 0 | 404 | 404 |
| 4.6 `/onDate` | 200 / 2 | 200 / 0 | 404 | 404 |

> ⚠️ 同一个「账户不存在」，5 个接口里有 1 个返回 400、4 个返回 200。
> 单看每个接口都能自圆其说，横着摆才矛盾。**这是契约一致性问题，不是单接口缺陷。**

### 5.2 `transactionId`（int）

| 输入 | 结果 |
|---|---|
| `12145`（存在） | 200 / 1 条 |
| `0` / `-1` / `1`（可解析但不存在） | 400 |
| `abc` / `1.5` / 空 / 溢出 | 404 |

### 5.3 `amount`（BigDecimal）

| 输入 | 结果 | 判定 |
|---|---|---|
| `300` / `300.00` | 同为 1 条（12145） | 数值语义，scale 不影响 |
| `100.0000` | 2 条 | 与 `100` 等价 |
| `0` | 1 条 | 库内存在 0 值流水 |
| `1e10` | 0 条 | 科学计数法合法 |
| `-100` | 0 条 | 负数合法，无匹配 |
| `abc` / 空 | 404 | 转换失败 |

### 5.4 `month`（String）

| 输入 | 结果 |
|---|---|
| `All` | 200 / 7 条（不过滤） |
| `11月` / `12月` | 200 / 5 条 / 2 条 |
| `11` / `Nov` / `nov` / `2026-11` / `'` | 200 / **7 条（静默全量）** |

### 5.6 日期类（`fromDate` / `toDate` / `onDate`）

「解析结果」列是**稳定**的（由 `SimpleDateFormat` 的行决定）；「结果条数」列**随数据漂移**，
下表是 11-21 快照下的值。

| 输入 | 解析成 | fromDate | toDate | onDate | 是否合法 |
|---|---|---|---|---|---|
| `11-11-2026` | 2026-11-11 | 1 条 | 4 条 | 0 条 | 合法，只是当天无数据 |
| `13-45-2026` | 2027-02-14 | 0 条 | 5 条 | 0 条 | 非法 |
| `02-30-2026` | 2026-03-02 | 5 条 | 0 条 | 0 条 | 非法 |

## 六、契约缺口

行为确定、但和通行契约冲突的地方。**只记录事实和影响，不提修复建议**——这个项目是公开演示系统，不产出缺陷单。

### 6.1 `type` 非法值导致 500

`CREDIT` / `credit` / `'` → 500。
影响：任何大小写变体都会让接口崩溃，且错误页暴露堆栈。

### 6.2 `type` 存在 SQL 注入

`0' OR '1'='1` → 21 条全表，`account_id` 过滤被绕过。
源码注释声明为「故意引入」，属演示桩。

### 6.3 `month` 无法识别时静默返回全量

`11` / `Nov` / `nov` / `2026-11` / `'` → 200 + 7 条（= 基线）。
影响：调用方无法区分「过滤生效但有 7 条」和「过滤完全没生效」。

### 6.4 账户不存在时的状态码不一致

`/transactions` 返回 400，其余 4 个返回 200 + 空。
影响：同一个错误条件，客户端要写两套处理逻辑。

### 6.5 日期解析未关闭 lenient

4 种非法日期全部被归一化后参与查询，无 4xx。
影响：`fromDate` 可能返回比「不过滤」更多的数据（7 条 > 基线 5 条）。

### 6.6 输出侧金额精度收窄（待验证）

库内 4 位小数 → 接口 2 位。
现有样本无法区分舍入与截断。**需要构造一条 4 位小数非零的流水才能确认**，属于数据受限，不是行为不明。

## 七、怎么用这张表写测试用例

这张表是**写用例的原料**，不是用例本身。转换方法：

| 表里的内容 | 变成什么用例 |
|---|---|
| 「合法值」列 | 正向用例：断言 200 + 精确条数 + 关键字段 |
| 「非法/边界值」列中标记 ✅ 或 ⚠️ 的 | 断言用例：把当前行为固化下来，行为变了就报警 |
| 标记 ❌ 的 | 反转断言：断言**正确行为**（如 400），标 `xfail` |
| 3.3 / 3.4 / 3.5 的通用契约 | 公共断言：每个列表用例都复用（排序、时区、精度） |
| 5.x 的横向表 | 一致性用例：同一个值喂给多个接口，断言响应一致 |

**不要做的**：把 106 条探测矩阵原样搬成 106 条用例。
探测是一次性实验，用例是可重复资产。以 `accountId` 为例，9 个变体里真正值得固化的只有 3 个：一个存在的、一个能解析但不存在的、一个不能解析的。其余（溢出、小数、注入串）属于「同一类错误的重复样本」，保留在探测脚本里即可。

**第二个坑：日期不要硬编码。**
种子流水的日期是 `CURRENT_DATE - N DAY` 算出来的，今天写 `11-09-2026`，明天就红。
正确做法是先拉一次全量列表，从返回的 epoch 反推 `MM-dd-yyyy`（按 UTC+8 还原，否则差一天），
再用它构造参数，断言「过滤是否生效」而不是「某天返回几条」。

本表对应的落地实现是 `tests/test_transactions.py`：
**44 条，36 passed / 8 xfailed**（2026-11-21 实测）。8 条 xfail 分别对应第六节的 6 条契约缺口。
